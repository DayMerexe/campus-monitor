# 第2章 需求分析

## 2.1 功能性需求

### 2.1.1 视频采集与AI检测

（1）多通道视频采集
①功能描述：系统需支持A、B、C三个独立通道的视频采集，每通道可接入MJPEG网络摄像头（ESP32-CAM）实时视频流或MP4本地视频文件，系统启动时自动匹配视频源，运行中可动态切换输入源类型。
②输入：ESP32-CAM的HTTP MJPEG实时流（Motion JPEG格式，320×240分辨率），或本地videos/目录下按通道前缀匹配的MP4视频文件。
③输出：解码后的OpenCV BGR格式图像帧，供YOLOv8n模型进行目标检测。
④处理流程：检测线程启动后调用视频源打开函数建立数据连接——MJPEG源通过HTTP持久连接（`requests.get(stream=True)`）逐chunk读取字节流，在字节缓冲区中搜索JPEG帧边界标记（`\xFF\xD8`和`\xFF\xD9`）提取完整帧数据；MP4源通过OpenCV `VideoCapture`逐帧读取，播到末尾时自动seek回开头实现循环播放。

（2）AI行人检测与计数
①功能描述：系统需对每路视频帧实时执行YOLOv8n深度学习推理，检测画面中的行人目标并统计人数，检测结果作为后续报警判定和联动决策的核心输入。
②输入：320×240分辨率的BGR图像帧。
③输出：每帧的行人数量（整数）、各检测框的边界框坐标（用于标注可视化）及对应置信度。
④处理流程：帧图像缩放到320×240后送入YOLOv8n模型进行推理（置信度阈值0.5），遍历输出的检测框列表，筛选类别ID为0（person类）的框进行计数；检测框坐标按缩放比例映射回原始分辨率，在原图上绘制标注框后通过MJPEG编码推送给前端展示。

（3）三通道并行调度
①功能描述：三个检测线程需同时运行且避免GPU资源的竞争冲突，各通道的检测帧率需保持在15fps以上以满足实时性要求。
②输入：三路独立的视频源连接。
③输出：三通道各自的人员计数、检测帧率和报警状态。
④处理流程：三通道检测线程以相位错开方式启动（A:0ms、B:16.7ms、C:33.3ms），将CUDA推理请求在时间轴上均匀散布；每线程以约50ms（20fps上限）为周期独立循环执行"读帧→推理→计数→报警判定→数据库写入→联动触发"流水线。

### 2.1.2 人流量监测与报警

（1）三级报警体系
①功能描述：系统需建立0级正常、1级黄色预警、2级红色报警三级报警体系，每通道可独立设置报警阈值，报警等级根据实时人数与阈值的比较关系自动判定。
②输入：各通道当前检测人数、黄色预警阈值（默认12人）、红色报警阈值（默认20人）。
③输出：各通道的当前报警等级（0/1/2），以及对应的LED灯光和蜂鸣器控制信号。
④处理流程：每帧检测完成后调用`get_target_level()`函数，将人数与两个阈值比较——人数不超过黄色阈值为0级，黄色阈值<人数不超过红色阈值为1级，人数>红色阈值为2级。

（2）对称防抖机制
①功能描述：需消除单帧误检/漏检导致的报警在阈值附近反复切换的问题，确保报警的稳定性。
②输入：连续帧的目标报警等级序列。
③输出：经过防抖确认后的最终报警等级。
④处理流程：采用"连续3帧确认+3秒锁定保护"对称防抖算法——上升方向需连续3帧目标等级高于当前等级才确认升级，下降方向同样需连续3帧目标等级低于当前等级才确认降级；等级切换后启动3秒锁定计时器，锁定期内任何变化请求均被忽略。

（3）报警事件记录
①功能描述：系统需以事件模式记录每次报警的完整生命周期，支持历史查询和统计分析。
②输入：报警等级变更事件（升降级时刻、当前人数）。
③输出：alarm_events数据库记录（含开始时间、结束时间、峰值人数、持续时长）。
④处理流程：等级从0升为非0时插入新记录并记录开始时间；持续期间累计峰值人数；等级恢复为0时更新结束时间和持续时长。

### 2.1.3 联动决策与引导

（1）全局状态快照与策略判定
①功能描述：系统需每0.3秒汇总三通道的当前状态（人数、报警等级、火灾状态、活跃状态），根据所有安全通道的拥挤情况自动判定全局引导策略。
②输入：三通道快照（人数、报警等级、火焰状态、活跃状态、阈值参数）及设备绑定关系。
③输出：四种全局策略之一（all_clear/guided/degraded/emergency）及对应的人流引导推荐文案。
④处理流程：在互斥锁保护下遍历三通道获取状态快照→排除火灾和非活跃通道→筛选安全通道→计算各安全通道饱和度（`sat = count / threshold_warn`）→按决策树判定策略：无活跃通道或无拥挤→all_clear；有拥挤但存在畅通安全通道→guided（按饱和度升序推荐）；所有安全通道均饱和→degraded（建议分批通行）；所有通道火灾→emergency（紧急疏散）。

（2）多出口引导推荐
①功能描述：在guided策略下，系统需按各安全通道的相对拥挤程度排序推荐最优疏散出口，并在仪表盘和钉钉通知中展示推荐列表。
②输入：各安全通道的饱和度值（0.0-∞）。
③输出：按饱和度升序排列的推荐出口列表及对应饱和度百分比。
④处理流程：筛选alarm_level=0且饱和度<0.8的畅通安全通道，按饱和度升序排列，生成"建议人员前往：出口B（饱和度30%）、出口C（饱和度50%）"格式的推荐文案。

（3）每设备独立指令生成
①功能描述：系统需为每个在线且已绑定的STM32设备生成独立的控制指令，指令内容根据该设备绑定通道的报警状态差异化生成。
②输入：设备绑定关系、绑定通道的当前报警等级和火灾状态。
③输出：每设备的`LV:X,BUZ:Y,SERVO:Z`格式控制指令。
④处理流程：遍历所有在线设备→根据绑定通道的fire/alarm_level计算lv（火灾或手动报警强制为2）→buz在lv≥1时置1→servo在lv≥2时置1→生成指令字符串→通过MQTT定向发送至对应设备的alarm Topic。

### 2.1.4 硬件执行控制

（1）STM32执行器驱动
①功能描述：STM32微控制器需接收来自MQTT的控制指令，驱动红黄双色LED、有源蜂鸣器和SG90舵机闸门执行对应的输出动作。
②输入：MQTT下发的`LV:X,BUZ:Y,SERVO:Z`控制指令（通过ESP8266 UART透传）。
③输出：PE5（黄灯）、PB5（红灯）、PB8（蜂鸣器）的GPIO电平，以及PA6（TIM3 CH1）的PWM信号。
④处理流程：USART2接收中断按`\n`帧边界累积字节→接收到完整行后用`sscanf`解析三个字段→在无火焰报警覆盖的条件下调用`set_outputs(lv)`驱动对应GPIO和舵机状态机。

（2）火焰传感器本地应急响应
①功能描述：火焰传感器需通过STM32本地直连实现独立于网络和PC的火灾检测与应急响应，确保在通信中断或PC宕机时系统仍能触发硬件报警。
②输入：PA0引脚数字电平（低电平=检测到火焰）。
③输出：本地驱动的全硬件输出（红灯常亮+蜂鸣器鸣响+舵机开门）及上行MQTT火焰状态消息。
④处理流程：主循环每100ms轮询PA0电平→经3帧防抖确认（连续3次低电平确认触发，连续3次高电平确认解除）→触发后`flame_alarm=1`，立即调用`set_outputs(2)`驱动全部输出→通过USART2发送`FLAME:1\n`至ESP8266上行MQTT。

（3）非阻塞舵机控制
①功能描述：舵机闸门动作（1200ms持续时长）不得阻塞火焰传感器轮询和UART数据接收。
②输入：舵机动作触发信号（开门/关门）。
③输出：50Hz PWM信号（CCR1=300对应开门正转，CCR1=1200对应关门反转，CCR1=750对应停止）。
④处理流程：采用非阻塞状态机——`servo_open_gate()`设置`servo_state=1`并记录启动时刻后立即返回；`servo_tick()`在主循环每轮被调用，检测动作时间是否达到1200ms，到期后将CCR1恢复至750停止位。

### 2.1.5 数据可视化与交互

（1）Web仪表盘实时监控
①功能描述：前端仪表盘需以单页面应用形式提供三通道视频实时预览、人流量动态折线图、联动推荐面板和系统控制栏四大功能区域。
②输入：`/dashboard`接口返回的三通道合并状态（人数、报警等级、帧率、火灾状态）、折线图历史数据、推荐信息；`/video_feed/<ch>`接口的MJPEG视频流。
③输出：三通道视频窗口（含人数叠加和报警状态灯）、Chart.js动态折线图、推荐出口面板、阈值调节/视频源切换/设备绑定控制栏。
④处理流程：前端每1秒轮询`/dashboard`接口刷新全部状态→各通道`<img>`标签每200ms刷新MJPEG流src→Chart.js根据活跃通道动态管理dataset（仅活跃通道显示折线，暂停通道自动移除）→`spanGaps: true`确保跨数据空缺的连续绘制。

（2）应急双态UI切换
①功能描述：系统需在正常状态和紧急状态之间自动切换仪表盘视觉模式，紧急状态下突出疏散引导信息。
②输入：全局策略类型（是否为emergency）和火焰报警状态。
③输出：正常模式（深色玻璃态，三通道视频+折线图+温和推荐面板）或紧急模式（红色顶部栏+折线图折叠+推荐面板放大突出）。
④处理流程：任意通道检测到火灾或手动报警激活时，前端根据`strategy==='emergency'`或`any_fire`条件切换CSS类→顶部栏背景变红并显示"⚠ 紧急状态"横幅→折线图区`max-height`折叠至最小→推荐面板字体放大并置顶。

（3）历史数据查询与回放
①功能描述：系统需支持按时间范围和通道查询历史检测记录，并提供数据回放模式。
②输入：查询时间范围（起始/结束ISO时间戳）、目标通道。
③输出：符合条件的历史检测记录列表及对应的折线图可视化。
④处理流程：前端发送查询参数至`/history` API→后端查询SQLite detection_records表（按时间戳过滤）→返回JSON数组→前端以Chart.js渲染选中时间段内的折线图。

### 2.1.6 通知推送

①功能描述：系统需在报警触发、升级和解除时通过钉钉群机器人向管理人员推送实时通知，通知内容应包含通道信息、人数、报警等级、推荐引导策略和所有通道概览。
②输入：报警触发事件（通道、等级、人数、全局策略、各通道状态）。
③输出：markdown格式的钉钉群消息卡片（含标题、引导文案、三通道概览、消防提示）。
④处理流程：`alarm_notify()`构建四级markdown消息（标题行→引导行→三通道概览→消防提示）→调用钉钉Webhook API发送→分级冷却机制控制发送频率（火灾始终发送、红色30秒冷却、黄色60秒冷却、解除30秒冷却）→级别升级穿透冷却、火灾穿透所有冷却。

## 2.2 非功能性需求

### 2.2.1 性能需求

①端到端响应延迟：从视频帧采集完成到STM32执行器GPIO电平变化的软件链路总延迟应控制在1秒以内。
②检测帧率：三通道并行运行时每通道检测帧率不低于15fps，单通道空载时不低于20fps。
③GPU利用率：三通道同时运行时GPU利用率峰值不超过80%，预留算力余量。
④前端刷新：仪表盘数据刷新间隔不超过1秒，视频画面刷新间隔不超过500ms。
⑤MQTT消息：单设备控制指令间隔不小于0.5秒，避免broker链路拥塞。

### 2.2.2 可靠性需求

①双通道冗余：AI视觉检测和本地火焰传感器构成两路独立检测通道，任一路失效时另一路应能独立完成应急检测和硬件触发。
②断线重连：WiFi和MQTT连接中断后应具备自动重连能力，重连退避基数2秒、上限60秒。
③遗嘱消息：ESP8266异常断线时MQTT Broker应在5秒内自动发布offline遗嘱消息，PC端据此标记设备离线并从联动决策中排除。
④火焰防抖：火焰传感器需经连续3帧（约300ms）确认才触发报警，避免电磁干扰误报。
⑤数据持久化：检测记录和报警事件应实时写入SQLite数据库，断电或程序异常退出不丢失已写入数据。

### 2.2.3 可扩展性需求

①多设备自动发现：服务端通过MQTT通配符订阅自动感知新ESP8266设备上线，无需预先配置设备清单或重启服务。
②通道独立启停：各监测通道可独立启动/暂停，互不干扰，暂停的通道自动从折线图和联动决策中排除。
③阈值独立配置：每通道的黄色预警和红色报警阈值可独立设定并通过前端实时调整，无需重启检测线程。
④视频源灵活切换：每通道支持MJPEG实时流和MP4本地文件两种视频源类型，可在运行时通过API动态切换。

### 2.2.4 可用性需求

①操作简洁：前端仪表盘的主要操作（启停监测、阈值调节、视频源切换、设备绑定）应在2次点击内完成。
②状态可见：各通道的实时人数、报警等级、连接状态和设备在线状态应一目了然，以颜色编码（绿/黄/红）提供直观的状态感知。
③响应式布局：仪表盘应适配桌面端（≥1024px宽）和移动端（≤680px宽）两种视口，移动端三通道由水平排列切换为垂直堆叠。
④安装部署：除PC（用于YOLO推理）外，硬件组件均为市售通用模组，无需定制开发或专用工具，整体硬件成本控制在百元级别。

## 2.3 约束条件

### 2.3.1 硬件约束

①AI摄像头：ESP32-CAM（AI-THINKER），板载ESP32-S芯片和OV2640图像传感器，WiFi 802.11b/g/n，最高分辨率UXGA（1600×1200），实际使用QVGA（320×240），仅支持单一MJPEG HTTP客户端连接。
②WiFi桥接：ESP8266 ESP-01S模组，Tensilica L106 32位处理器，80MHz主频，WiFi 802.11b/g/n，通过UART与STM32通信。
③主控MCU：STM32F103ZET6，ARM Cortex-M3内核，72MHz主频，64KB SRAM，512KB Flash。
④舵机：SG90 360°连续旋转型，4.8-6V供电，50Hz PWM控制，1ms脉宽正转/1.5ms停止/2ms反转。
⑤火焰传感器：红外接收管模块，探测波长760-1100nm，DO数字输出，低电平触发。
⑥蜂鸣器：有源蜂鸣器模块，3.3-5V供电，约2300Hz频率。
⑦运算平台：PC主机，NVIDIA RTX 3060 Laptop GPU（6GB GDDR6），用于YOLOv8n模型推理。

### 2.3.2 技术约束

①目标检测模型：采用YOLOv8n（nano版本，约3.2M参数），基于COCO预训练权重直接部署推理，暂不执行自定义数据集微调。
②MQTT Broker：使用EMQ X公共Broker（broker-cn.emqx.io:1883），不搭建私有Broker。
③后端框架：Python 3 + Flask Web框架，PyTorch深度学习框架，paho-mqtt MQTT客户端库。
④前端技术：单页面HTML+CSS+原生JavaScript，Chart.js 4.x（CDN引入），不依赖前端构建工具。
⑤数据库：SQLite轻量级数据库，文件型部署，不依赖外部数据库服务进程。
⑥ESP8266固件：Arduino SDK + ESP8266WiFi库 + PubSubClient库。
⑦STM32固件：STM32CubeMX初始化配置 + Keil MDK-ARM编译，HAL库与寄存器操作混合编程。

## 2.4 数据需求

### 2.4.1 数据类型

①视频图像数据：MJPEG格式实时视频帧（ESP32-CAM）或MP4编码视频帧（本地文件），每帧分辨率320×240，颜色空间BGR。
②检测结果数据：每帧的行人检测框数量、各检测框的边界框坐标（x1,y1,x2,y2）及置信度，检测时间戳和通道标识。
③传感器数据：火焰传感器数字状态（0=正常，1=检测到火焰），每100ms更新一次。
④设备状态数据：各STM32设备的在线状态（online/offline）、绑定通道关系、最后通信时间。
⑤报警事件数据：每次报警的开始时间、结束时间、峰值人数、持续时长、关联通道。
⑥配置数据：各通道的报警阈值（黄色/红色）、视频源配置（类型+路径/URL）、设备绑定关系。

### 2.4.2 数据流向

①视频数据流：ESP32-CAM → WiFi HTTP MJPEG → PC端Python后端 → YOLOv8n推理 → 检测结果写入channel_state → MJPEG编码推流至前端`<img>`标签展示。
②传感器数据流：火焰传感器 → GPIO PA0 → STM32轮询防抖 → USART2 → ESP8266 UART透传 → MQTT publish → PC端回调更新devices字典 → 联动决策读取火焰状态。
③控制指令流：PC端coordinated_decision()生成指令 → MQTT publish至alarm Topic → ESP8266 subscribe接收 → UART透传 → STM32 USART2接收解析 → GPIO/PWM驱动执行器。
④通知数据流：PC端alarm_notify()构建markdown消息 → HTTP POST → 钉钉Webhook API → 钉钉群消息推送。
⑤存储数据流：检测线程每1秒写入detection_records表；报警事件触发/解除时写入/更新alarm_events表。

## 2.5 小结

本章从功能性需求、非功能性需求、约束条件和数据需求四个方面对系统进行了全面的需求分析。功能性需求覆盖了视频采集与AI检测、人流量监测与报警、联动决策与引导、硬件执行控制、数据可视化与交互、通知推送六大核心模块，每项功能采用"功能描述→输入→输出→处理流程"的统一格式进行详细说明。非功能性需求涵盖性能、可靠性、可扩展性和可用性四个维度，为系统质量属性设定了可量化的目标。约束条件明确了硬件选型和开发技术栈的限制，数据需求梳理了系统中涉及的数据类型及其流向。以上分析为后续的总体设计和详细实现提供了明确的依据和边界。
