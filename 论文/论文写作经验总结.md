# 毕设论文写作经验总结

> 适用场景：有完整项目代码，需要写成工科本科毕设论文（5章+结论标准结构）。
> 本文档供其他 AI 或新对话快速理解流程、避坑。

---

## 一、整体流程

```
项目代码+功能总结 → 读学校模板+优秀论文 → 定章节大纲 → 写.md源文件
→ python-docx组装正文 → 合并封面声明 → 格式校验修复 → 图表插入 → 终稿
```

**核心思路**：所有章节用 Markdown 写，脚本一键生成 .docx。好处：
- Markdown 便于 AI 协作和版本管理
- 格式变更只需改脚本重跑，不用手动调 Word
- Git 可 diff 每章修改

---

## 二、章节结构（5章+结论）

这是多数工科毕设的标准结构：

| 章 | 标题 | 字数 | 核心内容 |
|----|------|------|----------|
| 1 | 绪论 | ~4000 | 背景三段式(现实需求→技术现状→本课题意义) → 国内外研究现状 → 研究内容列表 → 论文结构 |
| 2 | 需求分析 | ~3000 | 功能描述→输入→输出→处理流程 四段式，每功能一个二级标题 |
| 3 | 总体设计 | ~6000 | 系统架构(物理+软件架构图) → 硬件选型/引脚 → 软件模块设计 → 通信协议 |
| 4 | 详细设计与实现 | ~5000 | 开发环境 → 各模块实现细节(带代码片段) → 模型训练 |
| 5 | 测试 | ~4000 | 测试环境 → 功能测试用例表 → 性能测试 → 结果分析 |
| 结论 | 结论 | ~1500 | 工作总结 → 创新点(3-4条) → 不足与改进方向 |

**关键经验**：
- "相关技术介绍"不独立成章，YOLO/MQTT/嵌入式/Web技术分散嵌入第3、4章对应位置
- 需求分析章采用"功能描述→输入→输出→处理流程"四段式，每个功能需求一个二级标题
- 测试要独立成章，含测试用例表（用例编号/测试项/预期/实际/通过）

## 三、工具链

### 3.1 核心脚本

```
论文/
├── assemble_thesis.py   # .md → 正文.docx（样式+字体+行距全部在脚本中设置）
├── merge_thesis.py      # 封面与声明.docx + 正文.docx → 终稿.docx
├── generate_cover.cjs   # docx-js 生成封面与声明.docx（含艺术字校名）
└── generate_drawio.py   # 生成 .drawio 参考模板
```

### 3.2 assemble_thesis.py 要点

- 用 `python-docx` 库
- **样式必须在脚本中硬编码**：字体(SimHei/SimSun)、字号(H1=15pt/H2=14pt/H3=13pt/正文=12pt)、行距(固定20pt)、首行缩进(2字符=480twips)
- 中文字体必须同时设 `w:ascii` 和 `w:eastAsia`，否则中文渲染异常
- 行距用 `lineRule=exact` + `line=400`(20pt) 的 XML 方式设置，不要用 `Pt(20)`（会被错误转换）

### 3.3 merge_thesis.py 要点

- 两段 docx 合并后，样式可能丢失或冲突
- 必须在合并后执行 `_fix_merged_styles()`：直接操作 XML 创建/覆盖 Normal、Heading1-3 样式
- docx-js 生成的封面用 'Heading1' ID（无空格），python-docx 也用同样 ID，合并后不会冲突
- 页眉页码需在 merge 时处理：封面无页码、声明页无页码、正文阿拉伯数字页码

### 3.4 格式校验方法

```bash
# 解包终稿检查样式
python scripts/office/unpack.py 终稿.docx unpacked_check/
# 检查 word/styles.xml 中的样式定义
# 对比学校模板 unpacked_template/word/styles.xml
```

常见格式问题：
- Normal 样式字体不是宋体/12pt
- 行距不是固定值20pt
- H1 颜色不是黑色（docx-js 默认蓝色）
- 段落对齐不是两端对齐

## 四、模板匹配经验

### 4.1 从学校模板提取格式

1. 解包模板 .docx：`python scripts/office/unpack.py 模板.docx unpacked_template/`
2. 读 `unpacked_template/word/styles.xml` 找到各样式定义（字体/字号/段距）
3. 读 `unpacked_template/word/document.xml` 看标题示例的实际格式
4. **提取所有文本框标注**：模板中格式要求经常以文本框（textbox）形式标注在页面上。用 lxml 提取 `document.xml` 中所有 `w:txbxContent` 元素获取完整文本。我们提取了 40 个文本框，覆盖封面到致谢的全部格式要求
5. 参考往年优秀论文（pdf 转 txt 后读），对比写法、结构、排版

### 4.2 关键模板要求速查

从 TEXTBOX 提取出的常用格式：

| 元素 | 字体 | 字号 | 行距 | 其他 |
|------|------|------|------|------|
| 正文 | 宋体 + Times New Roman | 小四(12pt) | 固定 20pt | 首行缩进 2 字符，两端对齐 |
| H1 章标题 | 黑体 | 小三(15pt) | 固定 20pt | 段前 20pt 段后 20pt，居中 |
| H2 节标题 | 黑体 | 四号(14pt) | 固定 20pt | 段前 24pt 段后 6pt，左对齐 |
| H3 小节标题 | 黑体 | 小四(12pt) | 固定 20pt | 段前 12pt 段后 6pt，左对齐 |
| 表题 | 黑体 | 11pt | — | 表上方居中 |
| 图题 | 宋体 | 11pt | 单倍行距 | 图下方居中，段前 6pt 段后 12pt |
| 参考文献正文 | 宋体 + Times New Roman | 五号(10.5pt) | 固定 16pt | 段前 3pt，无缩进 |
| 封面标签 | 仿宋 | 三号(16pt) | — | — |
| 封面值/日期 | Times New Roman | 三号(16pt) | — | — |
| 页眉 | 宋体 | 五号(9pt) | — | 居中 |

## 五、AIGC 检测规避

这是当前学校审查的重点。我们经过两轮深度降重，总结出文字、格式、结构三个层面的策略。

### 5.1 结构降重：抽象层级提升（最根本）

这是通读完优秀论文后发现的根本问题。原论文读起来像"AI 分析一份已完成的项目代码"——需求分析章写的是"YOLOv8n 模型推理后筛选 person 类别统计人数"，而不是"系统应能识别画面中的人员目标"。优秀论文的需求分析和设计章不出现任何实现细节。

**抽象层级的对照**：

| 章节 | 改前（代码文档风格） | 改后（学术论文风格） |
|------|---------------------|---------------------|
| 节标题 | `detector.py`、`app.py` | 检测引擎模块、联动决策模块 |
| 需求分析 | "模型推理后统计person类别" | "系统应能识别画面中的人员目标" |
| 系统设计 | 函数名、引脚号(PA0)、定时器(TIM3)、MQTT Topic 字符串 | 全部移除，用功能描述替代 |
| 详细实现 | 逐函数代码走读 + 带编号伪代码(式4-1) | 设计思路 + 关键决策 + 折中说明 |
| 全文 | "约700行"、"约2800行"等行数统计 | 删除 |
| 全文 | API端点路径、CSS值、字节标记(\xFF\xD8) | 删除 |

**核心原则**：需求分析章用"应能…"句式（需求级），设计章用"采用…结构，因为…"句式（设计原理级），实现章用"实际部署中发现…因此选择…"句式（工程决策级）。叙述主体是"系统要做什么、为什么这样设计"，不是"代码怎么写的"。

### 5.2 文字降重

- **去掉AI连接词**："首先/其次/然后/最后"、"此外"、"同时"、"另外"
- **打破四段并列结构**：AI喜欢4段整齐排比，手动改成不规则的段落长度
- **去掉元话语**："值得注意"、"可以观察到"、"应该说"、"由此可见"
- **口语化过渡**：用"可以看到"、"实际运行时"、"这里的关键是"等自然过渡
- **精简冗余修饰**："极其重要"→"关键"、"显著提升"→"提升了"
- **替换禁用词**："随着...的发展"→具体说发展了什么；"在...方面"→直接说

### 5.3 格式降重：去除AI格式化痕迹

- **`**...**` 加粗强调**：AI 写作最典型的特征之一。AI 喜欢把核心概念用加粗强调，如"**双通道互补架构**"、"**缺乏完整的决策-执行闭环**"。全文清除 364 个星号标记（仅保留英文 Keywords 加粗，模板 TEXTBOX 13 要求）
- **标题 bold 双重加粗**：黑体（SimHei）本身就是粗重字体，代码中 `bold=True` 会触发 Word 仿粗体机制，结果为双重加粗。模板所有标题均不需要加粗
- **章末 `---` 分隔线**：Markdown 水平线在 docx 中无排版意义

### 5.4 图表降重

- **不要AI生成图**：学校能识别 Midjourney/DALL-E 等生成的示意图
- **手动画 draw.io 流程图**：用 .drawio 文件，在 draw.io 桌面版中手动调整线条位置、颜色、字体后导出 PNG
- **Excalidraw 手绘风格**可作为备选：roughness+hachure 填充，手工痕迹明显

### 5.5 整体原则

- 每段不要有完全相同的句式结构
- 适度使用口语化但不随意的表达
- 测试数据表格是"人写的"最强证据，多放真实测试结果

## 六、图表制作流程

### 6.1 架构图

1. 先用脚本生成 .drawio 参考模板（含基本框线和文字）
2. 在 draw.io 桌面版中打开，手动调整：拖动线条位置、修改配色、调整箭头样式
3. 导出 PNG（150 DPI 即可）
4. 同时保留 .drawio 源文件以备修改

### 6.2 照片/截图

- 系统运行截图：正常态 + 紧急态 + 折线图
- 实物照片：整体硬件连接图
- 钉钉通知截图

### 6.3 插入 docx

用 python-docx 的 `add_picture()` 插入，控制图片宽度在页面内容区域内（A4约14.6cm）。

## 七、踩过的坑

| 问题 | 原因 | 解决 |
|------|------|------|
| 封面生成中文乱码 | docx-js 不内嵌中文字体 | 指定 'SimHei'/'SimSun' 字体名 |
| .drawio 文件打开空白 | XML 属性值中 `<b>` 未转义 | 用 `xml.sax.saxutils.escape()` 转义所有属性值 |
| 合并后 Heading 样式丢失 | docx-js 和 python-docx 样式 ID 命名约定不同 | merge 后直接操作 XML 创建样式 |
| 行距设置无效 | python-docx `line_spacing=Pt(20)` 被错误转换 | 手动构建 XML：`<w:spacing w:line="400" w:lineRule="exact"/>` |
| 中文显示为方框 | 只设了西文字体未设东亚字体 | 同时设 `w:ascii` + `w:eastAsia` 字体属性 |
| 页码格式不统一 | 合并不处理 section 差异 | merge 脚本分别处理封面/声明/正文的 section 属性 |
| 参考文献格式混乱 | 来源不统一 | 统一用 GB/T 7714 格式，在 .md 中硬排好 |
| Excalidraw 渲染报错 | `txt` 参数覆盖了 `txt()` 函数 | 改参数名 |
| GBK 终端输出报错 | Node 输出含 ✓ 等 Unicode | strip 非 ASCII 字符后再 print |
| 标题 bold 双重加粗 | 黑体本身粗重，bold=True 触发仿粗体 | 所有标题移除 bold=True |
| `**...**` 加粗 = AI 特征 | AI 喜欢把核心概念加粗 | 全文清除，保留英文 Keywords（模板要求） |
| H3 小四应为 12pt | assemble_thesis.py 设了 13pt | 改为 12pt |
| H1 段前应为 20pt | 设了段前 40pt(800 twips) | 改为 400 |
| #### 四级标题无模板格式 | 模板只定义到 H3 | 标题升级为 ### + 编号，或改为正文加粗 |
| 章末 --- 分隔线 | Markdown 水平线渲染到 docx 无意义 | 删除 |
| 封面标签列字体 | 用了黑体，模板 TEXTBOX 2 要求仿宋 | 改为仿宋三号 |
| 封面值列字体 | 用了仿宋，模板 TEXTBOX 1 要求 Times New Roman | 改为 TNR 三号 |
| 表题/图题格式不同 | 表题黑体 11 磅(TEXTBOX 21)，图题宋体 11 磅(TEXTBOX 31) | 正则分两路匹配 |
| 参考文献格式独立 | 正文五号 10.5pt 行距 16 磅，无首行缩进 | parse_md_body 单独传参 |
| 格式靠 styles.xml 不够 | 文本框标注了 40 处格式要求不在样式表中 | 提取 w:txbxContent 全文逐条核对 |
| Word 锁定文件无法覆盖 | Word 打开 docx 时生成 ~$ 锁文件 | 版本递增命名（v10→v11），每次新版本删旧版 |

## 八、子对话并行策略

对于有 AI 协作工具的情况：

1. **主对话**控制全局：读模板 → 定大纲 → 分配子对话 → 审查合并
2. **子对话**在独立 git 分支写各自章节：
   - 论文前半（Ch1+Ch2）
   - 论文后半（Ch3+Ch4+Ch5）
   - 论文收尾（结论+参考文献+致谢+附录+摘要）
3. 子对话完成后 commit → 推送 → 主对话审查术语一致性和编号连续性 → 合并
4. 主对话运行 assemble 脚本生成最终 .docx

**如果不开子对话**（单人+AI），按章节顺序逐个写即可，流程一样。

## 九、给 AI 的启动 Prompt 模板

如果你想开新对话让 AI 帮忙写论文，可以这样 prompt：

```
我需要为一门工科毕设写论文。项目是：[一句话描述项目]。
学校模板在 [模板路径]，往年优秀论文参考在 [参考路径]。

请按5章+结论结构写：
第1章 绪论（研究背景→国内外现状→研究内容→论文结构）
第2章 需求分析（功能需求四段式）
第3章 总体设计（架构+硬件+软件+协议）
第4章 详细设计与实现（环境+核心模块+关键代码）
第5章 测试（功能测试+性能测试+结果分析）
结论（总结+创新点+不足）

格式要求：宋体12pt正文/Times New Roman英文、固定行距20pt、首行缩进2字符、
两端对齐。H1黑体15pt居中、H2黑体14pt、H3黑体13pt。

每个章节先写 .md，确认后再用 python-docx 组装 .docx。
注意 AIGC 降重：不用AI连接词、打破对称句式、口语化过渡。

项目功能文档：[提供项目概述文档]
```
