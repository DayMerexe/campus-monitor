### 4.1.2 核心模块实现

#### 1. detector.py — 检测引擎

　　检测引擎是系统最核心的模块，约700行代码，实现了三通道并行检测、双视频源管理、YOLO推理流水线、报警防抖和联动决策触发。

　　**detect_loop主循环**。函数`detect_loop(channel)`作为每通道独立线程的入口，以约20fps为上限频率循环执行。核心循环体的伪代码如式（4-1）所示：

```
while True:
    if not channel_active[channel]: sleep(0.5); continue
    检查视频源配置是否变更 → 关闭旧源、打开新源
    if source is None: 调用_open_source(channel) 打开输入源
    frame = _read_frame(source)  # 统一帧读取接口
    if frame is None: 处理EOF/断连 → continue
    small = cv2.resize(frame, (320, 240))
    results = model(small, conf=0.5, verbose=False)
    count = sum(1 for box in results[0].boxes if box.cls[0] == 0)
    报警防抖判断(连续3帧确认升降级 + 3秒锁定)
    画框标注 + 写入channel_state
    每1秒写入detection_records表
    每0.3秒调用coordinated_decision()触发联动
    sleep使帧率不超过20fps上限
```

<p align="right"><b>式（4-1）</b></p>

　　检测循环内的两个关键时间间隔设计如下：检测周期上限为50ms（20fps），与ESP32-CAM最高帧率（约25fps）匹配，避免无效空帧读取；联动决策触发间隔为300ms，在响应实时性（过快会增加锁竞争和MQTT消息量）与检测周期（50ms）之间折中。

　　**MJPEG持久连接**。函数`_read_mjpeg(url)`实现了基于HTTP持久连接的MJPEG帧解析。关键技术细节包括：使用`requests.get(stream=True, timeout=(3,5))`建立流式HTTP连接，连接以`(url, threading.get_ident())`为键缓存在全局字典`_mjpeg_connections`中，实现per-thread连接隔离。字节缓冲区`buf`跨`read`调用保留，每次读取新chunk后追加到缓冲区尾部，在缓冲区中搜索`\xFF\xD8`（SOI）和`\xFF\xD9`（EOI）边界标记，提取完整的JPEG帧数据后由`cv2.imdecode`解码。当缓冲区超过100KB时截断保留最后50KB，防止内存无限增长。

　　**统一帧读取接口**。函数`_read_frame(source)`通过source参数的类型判断实现MJPEG和MP4的统一读取接口：当source为`tuple('mjpeg', url)`时，调用`_read_mjpeg(url)`读取MJPEG帧；当source为`cv2.VideoCapture`实例时，调用`source.read()`读取MP4帧。这一抽象使得检测主循环无需关心底层视频源类型。

　　**MP4 EOF循环播放**。当`_read_frame()`对MP4源返回None时（视频播到末尾），检测循环调用`source.set(cv2.CAP_PROP_POS_FRAMES, 0)`将帧指针seek回开头，并立即读取一帧验证seek成功。若seek失败（如文件被删除或编码损坏），释放VideoCapture对象并重新调用`_open_source()`。相比早期的`release()`+重新`open()`方案，seek方案避免了文件重新打开时的解码器重初始化延迟（约200-500ms），将EOF恢复时间从秒级降至毫秒级。

#### 2. app.py — 联动决策函数

　　联动决策函数`coordinated_decision()`是中央决策引擎的核心实现，约140行代码，在`coord_lock`互斥锁保护下执行四个阶段的处理。

　　**第一阶段：状态快照**。遍历A/B/C三个通道，在各自`channel_locks[ch]`锁保护下读取每通道的当前人数、报警等级、火灾状态、活跃状态和阈值参数，汇集到`snap`字典中。对于非活跃通道，人数和报警等级强制置为0。同时读取`device_bindings`快照和`communication.devices`设备状态快照。

　　物理火焰覆盖逻辑：遍历所有绑定关系，若对应设备在线且其`flame`字段为True，则将绑定通道的`snap[ch]['fire']`置为True。这一设计使得物理火焰传感器的状态覆盖模拟火焰状态，确保物理信号的权威性。

　　**第二阶段：四策略判定**。按以下顺序判定全局策略：
1. 活跃通道列表为空 → `all_clear`，消息"无活跃监测通道"
2. 安全通道列表为空（全部火灾）→ `emergency`，消息"所有通道发生火灾！请立即远离该区域"
3. 计算所有安全通道的饱和度：`sat[ch] = count / max(threshold_warn, 1)`
4. 所有安全通道的报警等级为0且饱和度<0.8 → `all_clear`
5. 存在畅通通道（alarm_level=0且sat<0.8）→ `guided`，按饱和度升序排列推荐出口
6. 否则 → `degraded`，将所有安全通道按饱和度升序排列

其中饱和度阈值0.8是可调参数，表示通道在达到黄色阈值80%时即被视为"接近饱和"。

　　**第三阶段：每设备指令生成**。遍历所有在线且已绑定的STM32设备，根据绑定的通道状态生成本次控制指令：
```python
lv = 2 if (snap[ch]['fire'] or manual_alarm_active) else snap[ch]['alarm_level']
buz = 1 if (lv >= 1) else 0
servo = 1 if (lv >= 2) else 0
per_device_msgs[dev_id] = f"LV:{lv},BUZ:{buz},SERVO:{servo}"
```
指令格式为逗号分隔的三个键值对，被STM32端`sscanf`解析。

　　**第四阶段：I/O输出**。所有MQTT发送操作在`coord_lock`临界区外执行，避免网络I/O在锁内阻塞检测线程。SIG广播消息在内容变化且间隔≥0.5秒时发送至所有在线设备。每设备的STM32指令同样在内容变化且≥0.5秒间隔时定向发送。节流机制在锁外进行时间比较和发送操作，锁内仅更新最后发送时间和内容记录。

#### 3. communication.py — MQTT通信

　　通信模块约200行代码，基于paho-mqtt库实现MQTT客户端管理、多设备状态跟踪和消息收发。

　　**通配符订阅与设备自动发现**。MQTT连接成功回调中订阅两个通配符Topic：`bishe/99257/+/status`和`bishe/99257/+/flame`。使用单级通配符`+`匹配任意device_id，实现对任意数量STM32设备的自动感知。

　　**消息回调解析**。函数`on_mqtt_message(client, userdata, msg)`在收到消息时执行：
1. 调用`_parse_topic(msg.topic)`从Topic中按`/`分隔提取`device_id`和`field`。
2. 调用`_ensure_device(device_id)`确保设备在`devices`字典中有条目（首次出现自动创建）。
3. 根据`field`类型更新设备状态：`status`字段更新online/offline状态，`flame`字段解析`FLAME:0`或`FLAME:1`更新火焰传感器状态。
4. 调用`_recalc_aggregates()`更新向后兼容的聚合属性`stm32_connected`和`flame_active`。

　　聚合属性`stm32_connected`定义为任一设备在线即为True，`flame_active`定义为任一设备火焰触发即为True。这些属性在detector.py和app.py中以`import communication`（模块引用，非from-import值快照）方式使用，确保总是读取最新值。

　　**每设备定向发送**。函数`mqtt_send_to(device_id, msg)`向指定设备的alarm Topic发送消息：Topic格式为`bishe/99257/{device_id}/alarm`，QoS=1（至少一次送达），消息以`\n`结尾供STM32按行解析。`mqtt_broadcast(msg)`作为广播接口，遍历所有在线设备各发一份。MQTT客户端采用异步连接（`connect_async`）和非阻塞循环（`loop_start`），避免网络延迟阻塞主线程。

#### 4. notify.py — 钉钉群机器人推送

　　钉钉推送模块约220行代码，实现了报警通知、恢复通知和发送冷却机制。

　　**markdown消息构建**。`alarm_notify(channel, level, count)`函数在报警触发时异步发送钉钉消息。消息内容以markdown格式构建，包含四个层次：
- 标题行：根据报警类型显示火灾🔥/红色报警🔴/黄色预警⚠️，附通道名称和当前人数。
- 引导行：根据联动决策的策略类型生成差异化文案——emergency显示"所有通道均不安全，请立即组织疏散"，degraded显示"各通道接近容量上限，请分批通行"并列出推荐出口，guided显示"请引导人员前往"后列出所有推荐出口及饱和度百分比，all_clear不输出引导行。
- 三通道概览：以图标（🔥/🔴/⚠️/🟢）+ 通道名称 + 人数 + 饱和度百分比的形式列出所有通道状态，当前报警通道标注"← 此处"。
- 消防提示：火灾通道特别标注"禁止进入此通道"。

　　**发送冷却机制**。函数`_should_send(channel, level, is_fire)`实现分级冷却判定：火灾消息始终发送（穿透所有冷却）；级别升级（黄→红）同样穿透冷却；同级或降级消息受冷却限制——红色级别30秒、黄色级别60秒。冷却计时器以通道为粒度独立维护（`_last_sent[channel]`），不同通道的报警互不干扰。

　　解除通知`alarm_clear_notify(channel, peak)`每通道独立冷却30秒（`_last_clear[channel]`）。通知内容包含峰值人数、其他仍在报警的通道提示（如有）、和所有通道的当前状态摘要。当所有通道均恢复正常时，显示"所有通道恢复正常通行"。

#### 5. STM32主控固件

　　STM32固件运行在STM32F103ZET6开发板上，基于HAL库和CMSIS编写，约320行用户代码。主要实现以下功能模块：

　　**servo_tick非阻塞状态机**。为防止舵机动作阻塞火焰传感器轮询和UART数据处理，舵机控制采用非阻塞状态机设计。`servo_open_gate()`设置`servo_state=1`并启动计时器后立即返回，`servo_tick()`在主循环每轮检查：若`servo_state`非零且当前时间距计时器启动已超过`SERVO_DURATION`（1200ms），则将CCR1恢复至750（停止）并重置`servo_state`为0。此设计使舵机在动作期间主循环仍能以<1ms的间隔轮询其他外设。

　　**火焰传感器3帧防抖**。与PC端人员检测的防抖机制类似，火焰传感器也采用3帧确认策略。每100ms检测一次PA0引脚电平：当连续3次读到低电平时确认火焰触发（`flame_alarm=1`），立即调用`set_outputs(2)`驱动全输出并通过UART发送`FLAME:1\n`；当连续3次读到高电平时确认火焰解除（`flame_alarm=0`），恢复到MQTT上次下发的输出状态并通过UART发送`FLAME:0\n`。100ms检测周期结合3帧确认，使得火焰探测的响应延迟约为300ms（确认触发）+ UART传输时间（<1ms），总响应时间远小于1秒。

　　**UART指令解析**。STM32通过USART2（PA2-TX, PA3-RX, 115200bps 8N1）与ESP8266通信。接收采用逐字节轮询方式（`HAL_UART_Receive(&huart2, &ch, 1, 1)`，超时1ms），以`\n`（LF）为帧边界，忽略`\r`（CR）。当收到完整行（以`\n`结尾）时，使用`sscanf(rx_buf, "LV:%d,BUZ:%d,SERVO:%d", &lv, &buz, &servo)`解析三个字段。解析成功后，仅在无火焰报警（`!flame_alarm`）时更新输出和舵机状态，确保火焰报警的最高优先级不被MQTT指令覆盖。

#### 6. ESP8266 MQTT透传固件

　　ESP8266固件约220行代码，实现了"MQTT↔UART双向透明桥接"功能。其设计要点包括：

　　**遗嘱消息（LWT）**。在`client.connect()`中通过最后两个参数设置LWT：`status_topic`为遗嘱Topic，`"offline"`为遗嘱Payload，`true`为retain标志。当ESP8266异常断线（网络中断或断电）时，MQTT Broker自动发布此遗嘱消息至status Topic，PC端收到后标记设备离线。`retain=true`确保即使PC端在设备断线时未在线，重连后仍能收到最后一条遗嘱消息。正常上线后ESP8266主动发布`"online"`消息覆盖遗嘱。

　　**双向串口透传**。下行方向：`callback()`函数在收到订阅Topic的消息时，通过`Serial.write(payload, length)`将消息原样发送至USART2→STM32。上行方向：`loop()`中检测`Serial.available()`后通过`Serial.readStringUntil('\n')`读取完整行，trim后通过`client.publish(flame_topic, line.c_str())`发布至MQTT。此设计使ESP8266对STM32和PC端完全透明——STM32像在使用有线串口，PC端像在直接与MQTT设备通信。

　　**LED状态指示**。利用ESP-01模组内置LED实现三级状态指示：常亮=上电/等待WiFi；500ms周期慢闪=WiFi已连接但MQTT未连接；200ms周期快闪=MQTT正常运行。收到消息时LED短暂闪烁（60ms），作为数据收发的物理指示。

### 4.1.3 YOLO模型训练

　　本系统使用YOLOv8n（nano版本）作为人员检测的基础模型。YOLOv8n是YOLOv8系列中最轻量的变体，拥有约3.2M参数量，在精度与推理速度之间取得了优秀平衡，特别适合本系统的实时检测需求。

　　目前系统运行使用的是YOLOv8n在COCO数据集上的预训练权重。COCO数据集包含80个目标类别，其中person类别的预训练检测精度已能较好地满足校园场景下的人员计数需求——在常规光照和中等密度场景下检测效果稳定，漏检率较低。在预训练权重的基础上，已完成了自定义数据集的准备工作，用于后续针对校园场景进行专门微调。

　　**数据集准备**。训练数据集由3330张标注图像组成，合并了公开行人检测数据集和自采集的校园场景图像。标注类别为单一person类（class_id=0）。数据集按8:1:1比例划分为训练集（2664张）、验证集（333张）和测试集（333张）。数据标注格式为YOLO格式（每行：`class_id cx cy w h`，坐标归一化到[0,1]区间）。

　　**训练参数配置**。训练采用Ultralytics YOLOv8框架，关键训练参数如表4-2所示。

<p align="center"><b>表4-2 YOLOv8n 训练参数配置</b></p>

| 参数 | 值 | 说明 |
|------|------|------|
| 模型 | yolov8n.pt | 基于COCO预训练权重微调 |
| 训练轮次 (epochs) | 50 | 在验证loss收敛后停止 |

### 4.2.3 测试结果分析

　　综合功能测试（27项）和性能测试（5项），共计32项测试全部通过，通过率100%。以下从各维度分析测试结果。

　　**功能完整性**。系统的8大功能模块——视频采集与AI检测、人流监测与报警、人流引导算法、硬件控制、钉钉通知、Web仪表盘、API路由和通信协议——均通过对应的功能测试用例验证。尤其联动决策的7个标准场景（GS-01至GS-07）覆盖了四策略的全部切换路径（含火灾排除、暂停通道排除、饱和度排序），验证了联动决策的正确性和鲁棒性。

　　**性能指标达标**。三通道同时运行下的检测帧率（A:18.5fps, B:17.8fps, C:17.2fps）均满足≥15fps的设计目标。端到端延迟（80-120ms）远超<1秒的设计目标（余量约88%），系统的实时响应能力充裕。GPU利用率峰值约75%，未触及性能上限，为未来扩展更多通道或更复杂模型留有空间。

　　**与设计目标对比**。将测试结果与第3章3.1.1节提出的五项设计原则逐一对比：

| 实时性<1s | 端到端延迟80-120ms，余量充足（表4-9） |
