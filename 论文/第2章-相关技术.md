# 第2章 相关技术介绍

## 2.1 目标检测技术

### 2.1.1 深度学习目标检测概述

　　目标检测（Object Detection）是计算机视觉的核心任务之一，要解决的问题是：在图像或视频帧中找出感兴趣物体，同时判断它是什么。在本系统中，目标检测技术用来从监控画面中检测行人并统计人数，是整个系统的感知基础。

　　基于深度学习的目标检测算法可大致分为两大类：Two-stage（两阶段）方法和 One-stage（单阶段）方法。

　　Two-stage 方法的代表包括 R-CNN 系列及其改进版本 Faster R-CNN[5]。第一阶段用区域提议网络（Region Proposal Network, RPN）在特征图上生成可能包含目标的候选区域，第二阶段对每个候选区域做分类和边界框精修。Two-stage 方法的检测精度通常较高，但候选区域要逐一处理，推理速度偏慢，在实时视频监控场景下帧率是一个瓶颈。

　　One-stage 方法直接在特征图上预测目标类别和边界框坐标，跳过了候选区域生成这一步，推理速度快很多。代表性算法包括 SSD（Single Shot MultiBox Detector）[6]和 YOLO（You Only Look Once）系列[2-3]。YOLO 系列把目标检测当成回归问题来做——将输入图像划分为 SxS 的网格，每个网格负责预测固定数量的边界框及其类别置信度。端到端的设计意味着 YOLO 在检测精度和速度之间取得了很好的平衡。

　　本系统选用 YOLOv8n 作为目标检测模型，选型逻辑是：YOLOv8 在 COCO 数据集上经过充分预训练，泛化能力有保证；n（nano）版本仅 3.2M 参数，模型文件约 6MB，在消费级 GPU（如 NVIDIA RTX 3060）上能跑到每秒几十帧，三通道并行完全够用；Ultralytics 提供的 Python API 封装得不错，跟 Flask 服务端集成起来很顺手。

### 2.1.2 YOLOv8 模型结构与原理

　　YOLOv8 的网络结构由三个核心部分组成：Backbone（骨干网络）、Neck（颈部网络）和 Head（检测头）[1]。

　　**Backbone —— CSPDarknet**。骨干网络负责从输入图像中提取多尺度特征。YOLOv8 沿用了 YOLOv5 的 CSPDarknet 架构，采用跨阶段部分连接（Cross Stage Partial, CSP）策略将特征图分成两部分，一部分过卷积模块处理，另一部分直接和处理后的结果在通道维度拼接。CSP 结构减少了计算量，同时让梯度流动更顺畅，有利于训练更深的网络。nano 版本的深度和宽度缩放因子分别设为 0.33 和 0.25，在保持足够特征提取能力的前提下，把参数量压到了极限。

　　**Neck — FPN + PAN**。颈部网络位于骨干网络和检测头之间，负责融合不同尺度的特征图。YOLOv8 采用特征金字塔网络（Feature Pyramid Network, FPN）与路径聚合网络（Path Aggregation Network, PAN）的组合结构。FPN 通过自上而下的路径将深层语义特征传递到浅层，PAN 则通过自下而上的路径将浅层的位置信息传递到深层。两者的结合使得网络能够同时获取丰富的语义信息和精确的位置信息，有利于检测不同尺度的目标。

　　**Head — Decoupled Head**。YOLOv8 采用了解耦检测头（Decoupled Head），将分类任务和定位任务分配到独立的分支处理。相比于 YOLOv5 的耦合头，解耦头减少了分类和回归任务之间的特征冲突，有助于提升检测精度。此外，YOLOv8 摒弃了传统的 Anchor-based 设计，采用 Anchor-free 的检测方式，直接预测目标中心点相对于网格的偏移量和边界框的宽高，简化了正负样本匹配策略，减少了超参数的数量。

　　在本系统的应用中，YOLOv8n 模型直接使用 COCO 数据集上的预训练权重进行推理部署。经实测评估，COCO 预训练权重对 person 类别的检测精度已满足校园场景下的人员计数需求，在常规光照和中等密度条件下漏检率较低，无需额外微调即可保证功能完整。同时，系统已完成校园场景自定义数据集（约 3330 张图像，涵盖不同光照条件、人群密度和拍摄角度）的采集和标注工作，为未来在更复杂场景下需要更高精度时进行模型微调提供了数据基础。推理时将输入帧缩小至 320×240 分辨率以平衡检测精度与速度，检测到的边界框坐标按比例映射回原始分辨率进行标注。仅统计类别为 person（COCO 类别 ID=0）且置信度高于 0.5 的检测框作为有效行人计数。

## 2.2 MQTT 通信协议

### 2.2.1 MQTT 协议概述

　　MQTT（Message Queuing Telemetry Transport）是一种基于发布/订阅（Publish/Subscribe）模式的轻量级消息传输协议，IBM 在 1999 年提出，2014 年成为 OASIS 官方标准[11]。MQTT 专门为资源受限的物联网设备和低带宽、不可靠网络环境设计，协议头最小仅 2 字节，支持双向通信，连接保持机制完善，在物联网领域用得非常多。

　　MQTT 协议的核心概念包括以下几个方面：

　　**发布/订阅模型**。和传统 HTTP 的请求/响应模型不同，MQTT 用的是发布/订阅的异步通信模式。设备（客户端）通过主题（Topic）区分不同类型的消息。发布者把消息发到某个主题，Broker（消息代理服务器）负责把消息转发给所有订阅了这个主题的客户端。这种解耦设计让发布者和订阅者彼此不需要知道对方的存在，系统扩展起来很灵活。

　　**服务质量（QoS）**。MQTT 定义了三级服务质量：QoS 0（至多一次），消息仅发一次，不确认，可能丢失；QoS 1（至少一次），消息发送后等待确认（PUBACK），确保至少送达一次，但可能重复；QoS 2（恰好一次），通过四步握手确保消息恰好送达一次，不丢不重，开销最大。在物联网场景中，QoS 1 通常在可靠性和开销之间取得较好平衡。

　　**遗嘱消息（Last Will Testament, LWT）**。客户端在连接 Broker 时可预先设置一条遗嘱消息。当客户端异常断线（非主动断开）且超过 Keep Alive 时间内未发送心跳时，Broker 自动将该遗嘱消息发布到指定主题。LWT 机制为设备在线状态的实时监控提供了标准化的解决方案。

　　**保留消息（Retained Message）**。发布者可设置消息的 Retain 标志，Broker 会存储该主题最后一条保留消息。当新的客户端订阅该主题时，Broker 立即向其发送这条保留消息，确保新订阅者能够及时获取最新状态。

### 2.2.2 MQTT 在本系统中的应用

　　本系统选择 MQTT 作为 PC 服务端、ESP8266 WiFi 模块和 STM32 控制板之间的核心通信协议，基于 EMQ X 公共 Broker（broker-cn.emqx.io:1883）进行消息中转。

　　**Broker 选型**。EMQ X（现名 EMQX）是一款开源的高性能 MQTT 消息中间件，支持百万级并发连接和分布式集群部署[12]。其提供的公共 Broker 服务免去了自建服务器的运维成本，适合原型验证和中小规模部署。服务端使用 paho-mqtt Python 客户端库（callback_api_version=VERSION2）实现 MQTT 通信。

　　**Topic 设计**。系统采用层次化的 Topic 命名规范，以 `bishe/99257` 为统一前缀，后接设备 ID 和消息类型。具体设计如下：

　　表2-1 系统 MQTT Topic 设计

　　| Topic | 方向 | QoS | 说明 |
　　|-------|------|-----|------|
　　| `bishe/99257/{device_id}/status` | 上行 | 1 | 设备在线状态（online/offline） |
　　| `bishe/99257/{device_id}/flame` | 上行 | 1 | 火焰传感器状态（FLAME:0/1） |
　　| `bishe/99257/{device_id}/alarm` | 下行 | 1 | 服务端向设备下发控制指令 |
　　| `bishe/99257/server/status` | — | 1 | 服务端遗嘱消息（LWT） |

　　服务端通过通配符订阅 `bishe/99257/+/status` 和 `bishe/99257/+/flame`，其中 `+` 为单层通配符，匹配任意设备 ID。这种设计使得服务端无需预先配置设备列表，新设备上线后自动被发现。

　　**控制指令格式**。服务端下发给 STM32 的控制指令采用 `LV:X,BUZ:Y,SERVO:Z` 的文本格式，以换行符 `\n` 作为帧边界。其中 `LV`（Level）为报警等级（0/1/2），`BUZ`（Buzzer）为蜂鸣器开关（0/1），`SERVO` 为舵机闸门指令（0/1）。文本格式便于调试和扩展，同时 STM32 端通过 `sscanf` 即可高效解析。

　　**遗嘱消息与设备管理**。每个 ESP8266 设备在连接 Broker 时设置 LWT 消息，意外断线时 Broker 自动向 `/status` 主题发布 "offline"。设备重连后立即发布 "online" 更新状态。服务端维护一个设备状态字典，通过回调函数实时更新各设备的在线状态和火焰传感器读数，并通过聚合属性（`stm32_connected`、`flame_active`）供联动决策引擎查询。

## 2.3 嵌入式系统技术

### 2.3.1 ESP32-CAM 视频采集

　　ESP32-CAM 是乐鑫科技（Espressif）推出的 ESP32 芯片摄像头开发板，集成了 240MHz 双核 Xtensa LX6 处理器、520KB SRAM 和 4MB PSRAM，板载 OV2640 图像传感器[15]。在本系统中，ESP32-CAM 负责视频采集和 MJPEG 流推送，是 AI 视觉检测通道的前端感知设备。

　　**OV2640 图像传感器**。OV2640 是 OmniVision 公司生产的 200 万像素 CMOS 图像传感器，支持 UXGA（1600×1200）及以下多种分辨率，内置 JPEG 硬件编码器，可直接输出压缩后的 JPEG 图像。在本系统配置中，分辨率设为 QVGA（320×240），与 YOLOv8 的推理输入分辨率一致，避免额外缩放开销。

　　**帧率优化**。在开发过程中，ESP32-CAM 在默认配置（20MHz XCLK）下实测帧率仅 2-3fps，远低于预期。排查发现 20MHz 是 OV2640 规格外的时钟频率，导致内部 PLL 无法稳定锁定。解决方案为将 XCLK 提升至 30MHz 并降低 JPEG 画质参数（quality=8），同时将分辨率固定为 QVGA。优化后实测帧率达到 20fps 以上，满足实时检测需求。固件层面还关闭了 WiFi 省电模式（`esp_wifi_set_ps(WIFI_PS_NONE)`）、限制 WiFi 协议至 802.11b/g/n HT20，并通过传感器 PWDN 引脚上下电和 SCCB 软复位消除 PLL 残留状态，确保每次上电后的稳定工作。

　　**MJPEG 视频流**。ESP32-CAM 固件基于 ESP32 Arduino SDK 中的 CameraWebServer 示例修改，运行一个轻量级 HTTP 服务器，在 `/stream` 端点输出 MJPEG（Motion JPEG）格式的视频流。MJPEG 以连续的 JPEG 帧组成流，帧间以 `--frame` 边界标记分隔。服务端使用 Python `requests` 库的 `stream=True` 模式建立持久 HTTP 连接，通过逐字节解析 JPEG 的起始标记（`\xff\xd8`）和结束标记（`\xff\xd9`）提取完整帧，再交由 OpenCV 和 YOLOv8 处理。需要注意的是，OpenCV 的 `VideoCapture` 默认基于 FFmpeg 后端，无法正确解析 ESP32-CAM 的 MJPEG 格式，需要绕过 FFmpeg 直接从 HTTP 原始字节流中手动提取 JPEG 帧。

### 2.3.2 STM32F103 控制平台

　　STM32F103ZET6 是本系统的核心嵌入式控制平台，采用 ARM Cortex-M3 内核，主频 72MHz，集成 512KB Flash 和 64KB SRAM，具有丰富的外设资源[16]。在本系统中，STM32 承担以下功能：解析来自服务端的 MQTT 控制指令，驱动红黄双色 LED 指示灯、有源蜂鸣器、SG90 舵机闸门等执行器件，以及采集火焰传感器状态并通过 MQTT 上行到服务端。

　　**开发环境与编程方式**。固件基于 STM32CubeMX 初始化外设配置，使用 Keil MDK-ARM 进行编译和烧录。编程采用 HAL（Hardware Abstraction Layer）库与直接寄存器操作混合的方式：GPIO 初始化、UART 通信等通用功能使用 HAL 库简化开发，而舵机 PWM 控制则直接操作 TIM3 寄存器（因 STM32F1 系列的 HAL_TIM 驱动文件缺失），其中包括配置预分频器（PSC=128-1）、自动重载寄存器（ARR=10000-1）以产生 50Hz PWM 信号，以及通过修改 CCR1 寄存器值（250=正转全速，750=停止，1250=反转全速）来控制 SG90 360° 旋转舵机。

　　**引脚分配**。表 2-2 列出了 STM32 在本系统中的主要引脚功能分配。

　　表2-2 STM32F103 引脚功能分配

　　| 引脚 | 功能 | 说明 |
　　|------|------|------|
　　| PE5 | 黄灯 LED | GPIO 输出，低电平有效 |
　　| PB5 | 红灯 LED | GPIO 输出，低电平有效 |
　　| PB8 | 蜂鸣器 | GPIO 输出推挽，高电平触发 |
　　| PA6 | 舵机 PWM | TIM3 CH1，50Hz PWM |
　　| PA0 | 火焰传感器 | GPIO 输入上拉，低电平触发 |
　　| USART2 TX/RX | ESP8266 通信 | 115200 8N1，双向透传 |
　　| USART1 TX/RX | 调试串口 | 预留，PA9/PA10 |

　　**火焰传感器防抖**。火焰传感器通过 PA0 引脚输入（内部上拉，低电平有效），在主循环中以 100ms 为检测周期。为避免电磁干扰导致的误触发，采用与报警防抖相同的"连续三帧确认"策略：仅当连续三次读取均为有效触发信号时，才确认火灾发生；同样地，仅当连续三次读取均为无效信号时，才确认火灾解除。火灾触发后立即通过 USART2 发送 `FLAME:1\n` 到 ESP8266 上行至 MQTT，火灾解除后发送 `FLAME:0\n`。

　　**非阻塞舵机控制**。舵机控制采用非阻塞状态机设计，在主循环中通过 `servo_tick()` 函数检查动作是否完成。开门动作设置 CCR1=300、持续 1200ms 后自动停止（CCR1=750）；关门动作设置 CCR1=1200、同样持续 1200ms 后自动停止。非阻塞设计避免了使用 `HAL_Delay()` 造成的主循环阻塞，确保火焰传感器检测和 MQTT 消息接收不受舵机动作的干扰。

### 2.3.3 ESP8266 WiFi 透传

　　ESP8266 是乐鑫科技推出的低成本 WiFi SoC，集成了 32 位 Tensilica L106 处理器和完整的 TCP/IP 协议栈。在本系统中，ESP-01S 模组（基于 ESP8266）作为 STM32 与服务端之间的 WiFi-MQTT 通信网桥。

　　**固件设计**。ESP8266 固件基于 Arduino SDK 开发（使用 ESP8266WiFi 库和 PubSubClient 库），编译后通过 USB-TTL 模块烧录。固件启动后首先连接指定 WiFi 网络，随后连接 MQTT Broker 并订阅下行指令 Topic（`bishe/99257/{DEVICE_ID}/alarm`）。收到下行消息后，通过硬件串口（115200 8N1）原样转发给 STM32 的 USART2。同时，ESP8266 持续监听串口，当 STM32 有数据发送时（如 `FLAME:1\n`），读取完整的一行并发布到上行火焰状态 Topic（`bishe/99257/{DEVICE_ID}/flame`）。这种双向透传机制使得 STM32 无需直接处理网络协议，专注于本地控制逻辑。

　　**多设备支持与设备 ID**。通过在固件顶部定义 `DEVICE_ID` 宏（如 `stm32_01`、`stm32_02`），同一份固件代码经修改一个字符串后即可烧录至不同的 ESP8266 模块，实现多设备的即插即用。Topic 和 Client ID 均由 DEVICE_ID 自动拼接生成，确保每个 STM32 设备拥有独立的通信通道。

　　**状态指示与重连**。ESP-01S 板载 LED 用于指示工作状态：常亮为初始化/等待 WiFi，慢闪（500ms 周期）为 WiFi 已连接但 MQTT 未就绪，快闪（200ms 周期）为 MQTT 已连接正常运行。收到消息时 LED 短暂闪烁（60ms）提供数据收发视觉反馈。WiFi 和 MQTT 都实现了指数退避自动重连机制（退避基数 2s，上限 60s），确保在网络临时中断后能够自动恢复通信。

## 2.4 Web 开发技术

### 2.4.1 Flask 轻量级 Web 框架

　　Flask 是基于 Python 的轻量级 Web 应用框架，由 Armin Ronacher 在 2010 年创建[17]。Flask 遵循微内核设计：核心只有路由分发（Werkzeug WSGI 工具包）和模板渲染（Jinja2 模板引擎）两个基础组件，其余功能（数据库 ORM、表单验证、认证等）通过扩展机制按需添加。这种设计思路让 Flask 在中小型项目和快速原型开发中很受欢迎。

　　本系统选 Flask 而不是 Django 等全栈框架，原因是：系统的后端逻辑以视频处理和 MQTT 通信为主，Web 服务只是控制面板和数据接口，Flask 的轻量特性刚好匹配；Flask 原生支持多线程模式（`threaded=True`），能同时处理多个视频流请求（`/video_feed/<channel>`）和 API 轮询，仪表盘的多路并发需求能覆盖；Python 生态跟 YOLOv8（Ultralytics 基于 PyTorch）和 paho-mqtt 库完全一致，不用跨语言对接。

　　**路由与 API 设计**。系统共定义 15 个 API 路由（详见第 4 章），按照功能类型可分为：页面路由（`/` 返回仪表盘 HTML）、视频流路由（`/video_feed/<channel>` 返回 MJPEG multipart 响应）、状态查询路由（`/dashboard`、`/status`、`/history`、`/alarms`）、控制操作路由（`/set_threshold`、`/set_source`、`/control`、`/fire_simulate`、`/bind_stm32`、`/toggle_monitoring`、`/replay`）和设备管理路由（`/get_bindings`、`/list_videos`）。路由设计遵循 RESTful 风格，GET 请求用于查询，POST 请求用于修改状态。

### 2.4.2 前端可视化技术

　　系统前端是单页 Web 仪表盘（SPA 架构的简化变体），全部代码集中在一个 HTML 文件里（约 1800 行），不依赖前端构建工具，外部库通过 CDN 引入。

　　**Chart.js 动态折线图**。Chart.js 是一款基于 HTML5 Canvas 的开源图表库，支持折线图、柱状图、饼图等类型，动画流畅、配置灵活[19]。本系统为每个活跃监测通道创建独立的折线图数据集（dataset），记录该通道的历史人流量变化。几个实现细节：时间戳截断毫秒部分（`timestamp.split('.')[0]`）实现三通道秒对齐的共享 X 轴；`spanGaps: true` 选项让折线跨过短暂丢帧的缺口，不会断开；active 通道才展示折线（动态 dataset 管理），暂停的通道自动从图表移除；刷新频率每秒一次，跟数据库写入频率（1s）对齐；折线图高度用 CSS 固定在 280px，防止数据多了纵向无限拉长。

　　**MJPEG 视频流展示**。三个通道的视频画面通过 HTML `<img>` 标签直接渲染 MJPEG 流（`src="/video_feed/A"` 等）。前端用的是固定 200ms 间隔的心跳轮询，而不是长连接事件推送（SSE）。选轮询的原因很实际——浏览器会把卡住的 MJPEG 流判定为死连接然后自动发起重连，如果用 SSE 会导致 Flask 线程泄露。通道暂停时显示灰色蒙层和"监测已暂停"提示文字，摄像头没连上时显示占位提示。

　　**应急双态模式与响应式布局**。仪表盘具有常规和紧急两种视觉状态。常规状态显示三通道视频窗口和折线图，推荐面板为绿色/黄色风格；紧急状态（策略为 emergency 时）顶部栏变为红色警示色，折线图折叠隐藏以突出疏散指令，推荐面板切换为紧急疏散文字并置顶。响应式布局通过 CSS `@media (max-width: 680px)` 媒体查询适配移动端：三通道由水平排列切换为垂直堆叠，字体和间距适当缩小，确保在手机屏幕上可操作。
