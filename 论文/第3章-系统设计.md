# 第3章 总体设计

## 3.1 系统总体架构

### 3.1.1 设计目标与原则

本系统的设计目标是构建一套面向应急场景的校园人流量监控与引导管理系统，在正常通行和火灾等紧急情况下，对教学楼多出口通道进行实时监测、智能评估与联动控制。系统设计遵循五个基本原则：

（1）双输入冗余。同时接入远程AI视觉检测与本地火焰传感器两路异构通道。AI通道以深度学习模型进行人员计数。火焰传感器直连微控制器，不依赖网络和PC即可独立响应。

（2）实时性优先。从视频采集到模型推理再到无线指令下发，端到端延迟控制在1秒以内。

（3）可扩展性。基于MQTT通配符订阅支持设备动态发现与接入。各通道可独立启停、配置阈值、切换视频源。

（4）低成本部署。除推理PC外硬件均为市售通用模组，整体成本控制在百元级别。

（5）应急双态模式。仪表盘具有正常监测和应急指挥两种界面模式。通道触发火灾时自动切换为应急模式，突出疏散引导信息。

### 3.1.2 系统物理架构

系统物理架构由感知层、运算层、通信层与执行层四层组成，如图3-1所示。感知层包括摄像头和火焰传感器。运算层为搭载GPU的PC主机，运行YOLO推理与联动决策。通信层以MQTT协议为核心，WiFi透传模块作为桥接器。执行层以ARM微控制器为核心，驱动LED、蜂鸣器和舵机闸门，并可本地直接响应火灾而不依赖网络链路。

### 3.1.3 系统软件架构

系统软件采用分层模块化架构，如图3-2所示，从下到上分为硬件固件层、通信层、数据层、检测引擎层、联动决策层和Web API层。

硬件固件层包含摄像头固件、WiFi透传模块固件和主控微控制器固件三个独立程序。通信层以MQTT协议为核心，负责PC与嵌入式设备之间的双向消息传递与即时通讯推送。数据层基于文件型轻量数据库，存储检测记录和报警事件。检测引擎层为每通道维护独立检测线程。联动决策层定期汇总各通道状态，执行防抖、态势评估和策略判定。Web API层提供RESTful接口，前端为单页面仪表盘应用。

## 3.2 硬件系统设计

### 3.2.1 硬件选型与参数

硬件选型的原则是"低成本、可复制、易扩展"，所有组件均为市售通用模组。各组件选型与参数如表3-1所示。

<p align="center"><b>表3-1 硬件组件选型清单</b></p>

| 组件 | 型号 | 核心参数 | 作用 |
|------|------|---------|------|
| AI摄像头 | ESP32-CAM | ESP32-S芯片, OV2640传感器, WiFi 802.11b/g/n | 视频采集与MJPEG推流 |
| WiFi桥接模块 | ESP8266 ESP-01S | 32位处理器, 80MHz, WiFi 802.11b/g/n | MQTT消息透传（PC↔MCU） |
| 主控MCU | STM32F103ZET6 | ARM Cortex-M3, 72MHz, 64KB SRAM, 512KB Flash | 执行器控制核心 |
| 舵机 | SG90 360°连续旋转型 | 4.8-6V, 50Hz PWM控制 | 模拟闸门开合 |
| 火焰传感器 | 红外接收管模块 | 探测760-1100nm, 数字输出, 低电平触发 | 火灾检测 |
| 蜂鸣器 | 有源蜂鸣器模块 | 3.3-5V供电, 内置振荡电路 | 声音报警 |

摄像头输出分辨率在图像质量和传输帧率之间取平衡。舵机选用连续旋转型号而非固定角度型号，通过PWM脉宽控制旋转方向和转速，适合模拟闸门的开合动作。

### 3.2.2 执行器控制逻辑概要

STM32通过GPIO驱动LED指示灯、蜂鸣器和舵机，通过USART与ESP8266通信。系统通过LED灯光、蜂鸣器和舵机闸门实现三级差异化输出：正常通行时所有执行器静默，预警时黄灯闪烁，报警时红灯常亮、蜂鸣器鸣响、闸门打开。火焰触发时执行器输出最高等级，不受网络状态影响。详细引脚分配、具体输出定义与控制逻辑见第四章。

### 3.2.3 多场景模拟策略

受实物条件限制，系统采用"物理共享+逻辑独立"策略实现三通道验证，具体模拟方案见第五章测试环境。

## 3.3 软件系统设计

### 3.3.1 视频采集与AI检测模块

目标检测模型选型。系统选用YOLOv8n作为目标检测模型，属于One-stage检测算法，直接在特征图上回归目标位置和类别，推理速度显著快于Two-stage方法，更适合实时视频监控场景。nano版本约3.2M参数，在消费级GPU上单帧推理仅需15至25毫秒，三通道并行完全满足实时性需求。系统直接使用COCO预训练权重进行推理，其对人员类别的检测精度已满足校园场景需求。

视频流采集方案。ESP32-CAM通过WiFi推送MJPEG视频流至PC端。系统同时支持网络摄像头实时流和本地视频文件两种输入源，每个通道可独立配置并运行中动态切换。

多通道并行调度。三个检测线程共享GPU资源，系统通过各通道检测线程的启动相位错开，将推理请求在时间轴上均匀散布，避免三路同时竞争导致排队等待。

### 3.3.2 三级报警与防抖机制

报警子系统采用三级等级体系搭配对称防抖算法，兼顾检测灵敏度和报警稳定性。

三级报警等级定义。每通道独立维护两个可配置的阈值参数：预警阈值和报警阈值。预警阈值低于报警阈值，两者之间形成预警缓冲带。前端可在运行中调整任意通道的阈值，调整即时生效。报警等级由当前人数与两个阈值的比较关系确定，如式（3-2）所示：

<p align="center"><b>L<sub>target</sub> = 0（count ≤ warn）。1（warn < count ≤ red）。2（count > red）</b></p>
<p align="right"><b>式（3-2）</b></p>

对称防抖算法。单帧判定容易受偶发漏检或误检影响，导致报警在阈值附近反复触发和解除。系统实现了对称防抖机制：上升和下降方向均需连续多次确认后方切换等级，等级切换后进入锁定保护期，期间忽略反向变化请求。火焰传感器触发时，对应通道的等效报警等级强制设为最高，不受检测人数影响。具体防抖参数与实现细节见第四章。

### 3.3.3 联动决策与引导算法

联动决策模块定期汇总各通道状态并判定全局引导策略。传统方案以绝对人数排序推荐出口，忽略了不同通道阈值差异带来的容量感知偏差。本系统引入"饱和度"概念来反映通道相对于其容量的拥挤程度，定义为当前人数与预警阈值的比值，如式（3-3）所示：

<p align="center"><b>饱和度和i = count<sub>i</sub> / threshold_warn<sub>i</sub></b></p>
<p align="right"><b>式（3-3）</b></p>

四策略决策树。联动决策根据所有活跃通道的安全状况，在四个引导策略中选择其一，决策流程如图3-3所示：

（a）all_clear（全线畅通）：所有活跃且安全的通道均未触发报警且饱和度低于安全上限，无需进行人流引导。

（b）guided（引导推荐）：部分通道拥挤但存在至少一个畅通的安全通道，将畅通通道按饱和度升序生成推荐出口列表。

（c）degraded（降级通行）：所有安全通道均接近或超过容量上限，无畅通替代通道可用，按饱和度排序提示分批通行。

（d）emergency（紧急疏散）：所有活跃通道均有火灾，无安全通道可用，触发最高级别警报。

每设备差异化指令生成。系统支持多个执行设备分别绑定至不同监测通道，联动决策根据各设备所绑定通道的状态生成独立的控制指令。具体判定逻辑与指令生成实现见第四章。

### 3.3.4 数据持久化设计

系统采用SQLite进行本地持久化，选择理由为：嵌入式部署无需额外数据库服务进程、单日数据量有限、Python标准库内置支持零额外依赖。数据库包含检测记录表和报警事件表两张核心表，检测记录表按固定周期写入各通道快照数据供前端折线图展示，报警事件表以生命周期模式跟踪每次报警从触发到解除的完整过程。ER图见图3-X，详细表结构与字段定义见第四章。


### 3.3.5 前端仪表盘设计

仪表盘为单页面Web应用，基于Chart.js实现动态折线图和MJPEG视频实时预览。具有正常监测和应急指挥两种视觉模式——火灾触发时自动切换为警告色界面，突出疏散引导面板。支持桌面和移动端响应式布局。具体实现见第四章。

## 3.4 通信协议设计

### 3.4.1 MQTT Topic体系设计

系统采用基于Topic的MQTT发布/订阅模型，Topic按"项目前缀/设备标识/消息类型"三级结构组织。上行Topic包含设备心跳和火焰传感器状态，下行Topic承载控制指令，广播Topic发送仪表盘汇总信号。服务端通过MQTT单层通配符订阅实现新设备自动发现。完整Topic体系与通配符模式见第四章。

### 3.4.2 通信链路数据流

系统的通信数据流包含下行控制链路、上行传感链路和遗嘱消息机制三条路径，如图3-4所示。

下行链路（PC→执行器）。联动决策生成各设备的控制指令后，通过MQTT发布至对应设备的指令Topic。WiFi透传模块订阅该Topic，收到消息后通过串口转发至微控制器，由其解析后驱动对应的GPIO和PWM输出。

上行链路（传感器→PC）。微控制器轮询火焰传感器电平并经防抖确认后，将状态通过串口发送至WiFi透传模块，由透传模块通过MQTT发布至对应设备的状态Topic。PC端在MQTT回调中更新设备状态，联动决策在下一次执行时读取更新后的传感器状态。

遗嘱消息机制（LWT）。WiFi透传模块在MQTT连接时设置遗嘱消息。模块异常断线时，消息代理自动发布遗嘱消息，PC端标记对应设备为离线并从联动决策中排除。模块重连后恢复在线状态。

### 3.4.3 协议健壮性设计

系统在串口帧边界处理、MQTT消息节流、通知冷却分级和设备自动发现等方面实施了健壮性保障，具体实现策略见第四章。
