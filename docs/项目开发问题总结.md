## 问题 1：STM32 串口接收架构 — 轮询 vs 中断

### 现象
使用 `HAL_UART_Receive_IT()` 中断模式接收，回调中读取的字节始终为 0，后续 `HAL_UART_Receive()` 返回 `HAL_BUSY`。

### 根因
- 中断回调 `HAL_UART_RxCpltCallback()` 在 ISR 上下文中执行
- `rx_byte` 全局变量未正确初始化，默认值为 0
- 回调执行后未重启 `HAL_UART_Receive_IT`，状态机锁死在 `HAL_UART_STATE_BUSY_RX`

### 解决方案
**采用纯轮询模式**，彻底禁用中断接收及回调。

```c
while (1) {
    uint8_t ch;
    if (HAL_UART_Receive(&huart2, &ch, 1, 1) == HAL_OK) {
        HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_5);  // LED0 翻转 = 收到字节
        // ... 处理 ch
    }
}
```

**对应文件**: `stm32_serial_led/Src/main.c` 第 150-178 行

## 问题 2：数据解析协议 — 换行符依赖陷阱

### 现象
SSCOM 串口助手发送 `COUNT:0,ALARM:1` 时 STM32 无反应。

### 根因
初始代码等待 `\n` 才触发 `sscanf` 解析，而 SSCOM 默认不自动追加换行符。即使 Python 端广播带 `\n`，ESP8266 透传可能因分包而丢失。

### 解决方案
改为**逐字节处理 + 持续尝试匹配**，不依赖终止符：

```c
if (ch != '\r' && ch != '\n') {
    rx_buf[rx_idx++] = ch;
    if (rx_idx >= 63) rx_idx = 0;
    rx_buf[rx_idx] = '\0';

    int count = 0, alarm = 0;
    if (sscanf(rx_buf, "COUNT:%d,ALARM:%d", &count, &alarm) == 2) {
        // 触发动作
        rx_idx = 0;
    }
}
```

**对应文件**: `stm32_serial_led/Src/main.c` 第 150-178 行

## 问题 3：PA3 浮空噪声

### 现象
ESP8266 未连接时，`HAL_UART_Receive` 不断读到随机字节，`rx_buf` 被垃圾填满，LED0（调试用）疯狂闪烁。

### 根因
PA3 (USART2_RX) 配置为 `GPIO_MODE_INPUT` + `GPIO_NOPULL`，悬空状态下电平不确定。

### 解决方案
- 确保 ESP8266 始终连接
- 进入 `while(1)` 前清空 USART2 缓冲区（见问题 6）
- 如需更健壮：给 PA3 配置内部上拉 `GPIO_PULLUP`

**对应文件**: `stm32_serial_led/Src/usart.c`

## 问题 4：CubeMX 重新生成破坏 USART1

### 现象
CubeMX 中添加 USART2 后重新生成代码，USART1 TX/RX 失效（SSCOM 无法通信）。

### 解决方案
采用 **USART2-only 方案**，USART1 仅用于调试。CubeMX 重生成后需对比 `usart.c` 和 `gpio.c` 差异。

## 问题 5：AT 初始化导致 STM32 卡死

### 现象
含完整 AT 初始化代码的固件烧录后 STM32 不启动（LED 完全不闪），不含 AT 代码的最小固件正常工作。

### 排查方法
**逐条加回法**：从最小可工作代码开始，逐条加回指令：

| 测试 | 命令 | 结果 |
|------|------|------|
| 1 | `AT\r\n` | ✅ |
| 2 | `AT+CIPSTART` | ✅ |
| 3 | `AT+CIPMODE=1` + `AT+CIPSEND` | ✅ |

### 解决方案
关键是要给 ESP8266 足够时间：
- `AT+CWJAP` 后至少 **8 秒**等 DHCP 拿 IP
- `AT+CIPSTART` 后 **3 秒**等 TCP 握手
- **顺序不能乱**：必须先连 WiFi 再连 TCP

**对应文件**: `stm32_serial_led/Src/main.c` 第 111-122 行

## 问题 6：TCP 连接成功但 STM32 不收数据（最隐蔽 Bug）

### 现象
- Python TCP Server 显示 `✅ ESP8266 已连接`
- 网页点击报警按钮提示 `✓ 已发送`
- **但 STM32 LED 和蜂鸣器完全不响应**

### 根因
AT 初始化期间，ESP8266 回复了大量数据积压在 USART2 接收缓冲区：

```
AT\r\n\r\nOK\r\n
AT+CWMODE=1\r\n\r\nOK\r\n
WIFI CONNECTED\r\nWIFI GOT IP\r\n\r\nOK\r\n
CONNECT\r\n\r\nOK\r\n
AT+CIPMODE=1\r\n\r\nOK\r\n
AT+CIPSEND\r\n\r\n>
```

进入 `while(1)` 后，`rx_buf` 开头是 `"ATOKAT+CWMODE=1OK..."`，后续 TCP 数据 `"COUNT:0,ALARM:1"` 追加在垃圾后面，`sscanf` 从 `rx_buf[0]` 匹配，永远不成功。

### 解决方案
进入 `while(1)` 前清空 USART2 缓冲区：

```c
{
    uint8_t dump;
    while (HAL_UART_Receive(&huart2, &dump, 1, 2) == HAL_OK) {}
}
memset(rx_buf, 0, sizeof(rx_buf));
rx_idx = 0;
```

**对应文件**: `stm32_serial_led/Src/main.c` 第 124-130 行

## 问题 8：ESP8266 供电不足

### 现象
ESP8266 间歇性断连、TCP 连接不稳定、WiFi 扫描不到。

### 解决方案
- 使用独立 3.3V 电源模块（USB 转 3.3V）
- VCC-GND 并联 10μF + 100nF 去耦电容
- 独立供电时 GND 必须与 STM32 共地

## 问题 9：WiFi 初始化冗余 -- 自动连接优化 🔴【用户提出】

### 现象
STM32 启动耗时过长，约 15 秒的 AT 初始化序列中有大量冗余命令。

### 用户发现
> **用户提出**：既然我的 ESP8266 上电会自动连接手机热点（WiFi 参数保存在 flash 中），那 STM32 根本不需要发送 `AT+CWJAP`（连接 WiFi）和 `AT+CWMODE=1`（设置模式）和 `AT+CWQAP`（断开已有连接）。

### 解决方案
**精简后的 AT 初始化序列**（节省 ~10 秒）：

```c
HAL_UART_Transmit(&huart2, (uint8_t*)"AT\r\n", 4, 100);
HAL_Delay(500);

// 跳过 CWMODE / CWQAP / CWJAP — ESP8266 上电自动连 WiFi
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSTART=\"TCP\",\"192.168.4.140\",8888\r\n", 43, 500);
HAL_Delay(4000);

HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPMODE=1\r\n", 14, 100);
HAL_Delay(500);
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSEND\r\n", 13, 100);
HAL_Delay(500);
```

### 效果
- 启动时间从 ~15 秒缩短到 ~5 秒
- 代码更加简洁可靠

**对应文件**: `stm32_serial_led/Src/main.c` 第 112-122 行

## 问题 10：TCP 连接不稳定 -- 摄像头接入后断连

### 现象
> 用户描述："接上摄像头之后过一会就无法传输数据"

ESP8266 的 TCP 连接在 ESP32-CAM 开始传输视频后不定期断开，STM32 收不到后续指令。

### 根因
- TCP 连接没有心跳/保活机制，服务端无法及时检测死连接
- ESP32-CAM 大流量 WiFi 传输可能影响 ESP8266 的信号质量
- 断连后服务端 `tcp_clients` 列表中仍保留已断开的 socket，广播时报错

### 解决方案

**TCP 服务端添加 keepalive + socket 超时**：

```python
conn.settimeout(5.0)
try:
    conn.setsockopt(socket.SOL_SOCKET, socket.SO_KEEPALIVE, 1)
except:
    pass
```

同时在广播函数中增加死连接清理：

```python
with tcp_lock:
    dead = []
    for c in tcp_clients:
        try:
            c.sendall(msg.encode())
        except:
            dead.append(c)  # 标记死亡
    for c in dead:
        tcp_clients.remove(c)
```

**对应文件**: `campus_monitor/tcp_server.py` 第 38-48 行, `campus_monitor/tcp_server.py` 第 13-23 行

## 问题 11：检测稳定性 -- 报警频繁误触发

### 现象
人流量在阈值边界波动时，报警在"触发-解除"之间频繁切换，STM32 LED 闪烁不止。

### 解决方案
引入**三级防抖机制**：

```
连续 3 帧超过阈值 → 触发报警（防误报）
连续 3 帧低于阈值 → 解除报警（防早退）
状态切换后锁定 3 秒 → 不允许再次切换（防震荡）
```

```python
ALARM_CONFIRM = 3   # 连续确认帧数
ALARM_LOCK = 3.0    # 状态切换后锁定秒数

if not locked:
    if not alarm_active:
        if count > ALARM_THRESHOLD:
            consecutive_over += 1
            if consecutive_over >= ALARM_CONFIRM:
                alarm_active = True  # 🔔 真正触发
                last_state_change = now
```

**对应文件**: `campus_monitor/detector.py` 第 51-55 行, 第 109-142 行

## 问题 12：TCP 广播洪水 -- STM32 UART 溢出

### 现象
YOLO 以 ~15 FPS 检测，每帧都广播 `COUNT:x,ALARM:y`，STM32 的 UART 轮询（1ms 超时）来不及处理。

### 解决方案
**TCP 广播限速到 0.5 秒间隔**（最多 2 次/秒）：

```python
now2 = time.time()
if not manual_alarm_active and (now2 - last_tcp_send >= 0.5):
    alarm_val = 1 if alarm_active else 0
    tcp_broadcast(f"COUNT:{count},ALARM:{alarm_val}\n")
    last_tcp_send = now2
```

同时 DB 写入也限速到 2 秒间隔。

**对应文件**: `campus_monitor/detector.py` 第 160-172 行

### 解决方案

```html

```

用户聚焦输入框时，轮询不会修改输入框的值。

## 问题 14：MJPEG 流解析失败 -- VideoCapture 不兼容

### 现象
ESP32-CAM 修改参数（分辨率 QVGA、画质 50、XCLK 20MHz）后，`cv2.VideoCapture` 底层 FFmpeg 无法正确解析 MJPEG multipart 流，报 "Stream ends prematurely"，`/video_feed` 返回 500。

浏览器直接访问 `http://192.168.4.183:81/stream` 正常。

### 解决方案
**HTTP raw 直读 + 手动切帧**（替代 `cv2.VideoCapture`）：

```python
r = requests.get(ESP32_CAM_URL, stream=True, timeout=10)
buf = b''
for chunk in r.iter_content(chunk_size=1024):
    buf += chunk
    a = buf.find(b'\xff\xd8')   # JPEG SOI
    b = buf.find(b'\xff\xd9')   # JPEG EOI
    if a != -1 and b != -1:
        jpg = buf[a:b+2]
        buf = buf[b+2:]
        frame = cv2.imdecode(np.frombuffer(jpg, dtype=np.uint8), cv2.IMREAD_COLOR)
        # → YOLO 推理
```

**关键改动**：`detector.py` 中 `requests.get(stream=True)` + JPEG SOI/EOI 标记切帧 + `cv2.imdecode` 解码。

**对应文件**: `campus_monitor/detector.py` 第 59-91 行
