# STM32 + ESP8266 ESP-01S 串口通信排错指南

## 系统架构

```
Python Flask → TCP Port 8888 → ESP8266 (ESP-01S) → USART2 → STM32F103ZET6 → LED/蜂鸣器
```

- **STM32**: STM32F103ZET6, HSI 64MHz, HAL 库, Keil MDK-ARM (ARM Compiler V6)
- **ESP8266**: ESP-01S, AT 固件, 115200 8N1
- **USART1** (PA9/PA10): CH340 USB转串口，连接电脑调试
- **USART2** (PA2/PA3): 连接 ESP8266，轮询接收
- **LED**: 低电平有效 (GPIO_PIN_RESET=亮, GPIO_PIN_SET=灭)
- **蜂鸣器**: PB8, 高电平有效

## 硬件接线

```
STM32                    ESP8266 ESP-01S
─────────────────────────────────────
PA2  (USART2_TX)    →   RX
PA3  (USART2_RX)    →   TX
3.3V                →   VCC
3.3V                →   CH_PD (EN)    ← 必须拉高，否则模块不工作
3.3V                →   GPIO0          ← 正常运行模式（非烧录模式）
3.3V                →   GPIO2
3.3V                →   RST
GND                 →   GND
```

> **供电注意**: ESP8266 峰值电流可达 300mA+，建议独立 3.3V 供电，不要仅靠 STM32 板载 3.3V 引脚。

## 问题 1：接收架构选择——轮询 vs 中断

### 现象
使用 `HAL_UART_Receive_IT()` 中断模式接收，回调函数读取到的始终是 0，且后续 `HAL_UART_Receive()` 返回 `HAL_BUSY`。

### 根因
中断回调 `HAL_UART_RxCpltCallback()` 中读取未初始化的全局变量 `rx_byte`（默认值=0），且回调执行后 `huart->RxState` 未正确恢复，导致后续 `HAL_UART_Receive()` 认为接收仍在进行中。

### 解决方案
**采用纯轮询模式**，不使用中断回调：

```c
// main.c, USER CODE 3 (while(1) 循环内)
uint8_t ch;
int parsed = 0;

if (HAL_UART_Receive(&huart2, &ch, 1, 1) == HAL_OK) {
    // 收到1字节，处理
    parsed = 1;
}
```

**USER CODE 4 保持为空**（不实现任何中断回调）。

## 问题 2：数据解析——不用依赖换行符

### 现象
SSCOM 串口助手发送 `COUNT:0,ALARM:1` 时 STM32 无反应。

### 根因
SSCOM 默认不自动追加换行符，而代码等待 `\n` 才触发 `sscanf` 解析。

### 解决方案
逐字节处理，每收到一个非 `\r` `\n` 的字符就尝试匹配：

```c
// main.c, while(1) 内
uint8_t ch;
int parsed = 0;

if (HAL_UART_Receive(&huart2, &ch, 1, 1) == HAL_OK) {
    HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_5);  // LED0 翻转，调试用
    parsed = 1;
}

if (parsed) {
    if (ch != '\r' && ch != '\n') {
        rx_buf[rx_idx++] = ch;
        if (rx_idx >= 63) rx_idx = 0;
        rx_buf[rx_idx] = '\0';

        int count = 0, alarm = 0;
        if (sscanf(rx_buf, "COUNT:%d,ALARM:%d", &count, &alarm) == 2) {
            if (alarm == 1) {
                // 报警：LED 亮，蜂鸣器响
                HAL_GPIO_WritePin(GPIOE, GPIO_PIN_5, GPIO_PIN_RESET);
                HAL_GPIO_WritePin(GPIOB, GPIO_PIN_5, GPIO_PIN_RESET);
                HAL_GPIO_WritePin(GPIOB, GPIO_PIN_8, GPIO_PIN_SET);
            } else {
                // 解除
                HAL_GPIO_WritePin(GPIOE, GPIO_PIN_5, GPIO_PIN_SET);
                HAL_GPIO_WritePin(GPIOB, GPIO_PIN_5, GPIO_PIN_SET);
                HAL_GPIO_WritePin(GPIOB, GPIO_PIN_8, GPIO_PIN_RESET);
            }
            rx_idx = 0;  // 匹配成功后清缓冲
        }
    }
}
```

## 问题 3：PA3 浮空噪声

### 现象
ESP8266 未连接时，LED0 疯狂闪烁，`rx_buf` 被乱码填满。

### 根因
PA3 (USART2_RX) 悬空状态下电平不确定，`HAL_UART_Receive` 以 115200 波特率读到随机噪声字节。

### 解决方案
- 仅连接 ESP8266 后使用 USART2
- 或在进入 while 循环前清空 RX 缓冲区（见问题 6）

---

## 问题 4：CubeMX 重新生成后 USART1 失效

### 现象
在 CubeMX 中添加 USART2 后重新生成代码，USART1 的 TX/RX 不再工作（SSCOM 收不到也不能发送）。

### 根因
CubeMX 代码生成可能覆盖 USART1 的中断配置或引脚初始化。

### 解决方案
- 改用 USART2-only 方案处理 ESP8266 通信
- USART1 仅做调试用途时，不依赖它

## 问题 5：AT 初始化命令序列设计（最关键）

### 现象
完整 AT 初始化代码导致 STM32 启动时卡死（红灯不闪、黄灯不闪），但去除 AT 命令的极简固件正常运行。

### 排除过程
采用**逐条加回法**，从最简 `AT\r\n` 开始：

| 测试 | 命令 | 结果 |
|------|------|------|
| 1 | `AT\r\n` | ✅ 正常 |
| 2 | `AT+CIPSTART` | ✅ 正常 |
| 3 | `AT+CIPMODE=1` + `AT+CIPSEND` | ✅ 正常 |

**结论**：不是单条命令的问题，关键是要给 ESP8266 足够时间连 WiFi 拿 IP。

### 最终 AT 序列和延时

```c
// main.c, USER CODE 2

HAL_Delay(2000);  // 等 ESP8266 启动
HAL_UART_Transmit(&huart2, (uint8_t*)"AT\r\n", 4, 100);
HAL_Delay(500);

// 设置 Station 模式
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWMODE=1\r\n", 13, 100);
HAL_Delay(500);

// 连接 WiFi —— ⚠️ 必须等 8 秒让 DHCP 分配 IP
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWJAP=\"test\",\"wxh708023\"\r\n", 31, 200);
HAL_Delay(8000);  // ⬅ 8秒至关重要！

// 连接 TCP Server
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSTART=\"TCP\",\"192.168.4.140\",8888\r\n", 43, 500);
HAL_Delay(3000);

// 进入透明传输模式
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPMODE=1\r\n", 14, 100);
HAL_Delay(500);
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSEND\r\n", 13, 100);
HAL_Delay(500);
```

**总耗时约 15 秒**，关键点：
- `AT+CWJAP` 后至少 7-8 秒等待 DHCP
- `AT+CIPSTART` 后 3 秒等 TCP 握手
- 顺序不能乱：必须先在 WiFi 上拿到 IP，再发起 TCP 连接

## 问题 6：TCP 连接成功但 STM32 不收数据（最隐蔽的 Bug）

### 现象
- main.py 显示 `✅ ESP8266 已连接`
- 网页点击报警按钮显示 `✓ 已发送`
- `POST /control` 返回 `200`
- **但 STM32 LED 和蜂鸣器完全不响应**

### 根因
AT 初始化期间，ESP8266 通过 USART2 回复了大量数据：

```
AT\r\n\r\nOK\r\n
AT+CWMODE=1\r\n\r\nOK\r\n
WIFI CONNECTED\r\n
WIFI GOT IP\r\n\r\nOK\r\n
CONNECT\r\n\r\nOK\r\n
AT+CIPMODE=1\r\n\r\nOK\r\n
AT+CIPSEND\r\n\r\n>
```

这些字节积压在 USART2 的硬件接收缓冲区中。进入 `while(1)` 后，`HAL_UART_Receive` 首先读到这些垃圾数据。

垃圾数据从 `rx_buf[0]` 开始填充，比如 `"ATOKAT+CWMODE=1OKWIFI CONNECTED..."`。后续 TCP 数据 `"COUNT:0,ALARM:1\n"` 追加到已有数据后面，但 `sscanf` 始终从 `rx_buf[0]` 开始匹配，`rx_buf[0]` 是 `'A'`，永远无法匹配 `COUNT:...` 模式。

### 解决方案
进入 `while(1)` 循环之前，**先读空 USART2 缓冲区，再清空 rx_buf**：

```c
// 黄灯闪烁之前加上这段
{
    uint8_t dump;
    while (HAL_UART_Receive(&huart2, &dump, 1, 2) == HAL_OK) {}
}
memset(rx_buf, 0, sizeof(rx_buf));
rx_idx = 0;
```

- `HAL_UART_Receive(..., 1, 2)` — 2ms 超时，读到没数据为止
- `memset` — 确保 rx_buf 从 index 0 开始是干净的

## 问题 7：前端按钮不生效

### 现象
报警按钮生效但"解除"按钮没反应，点击后按钮无反馈。

### 根因
```javascript
const btn = action === 'alarm_on'
    ? document.querySelectorAll('button')[2]  // 实际拿到"解除"按钮
    : document.querySelectorAll('button')[3]; // undefined！不存在
```
页面只有 3 个按钮（索引 0/1/2），`[3]` 为 `undefined`，访问 `btn.textContent` 抛出 TypeError，`fetch` 从未执行。

### 解决方案
```javascript
const btn = action === 'alarm_on'
    ? document.querySelectorAll('button')[1]  // "报警"按钮
    : document.querySelectorAll('button')[2]; // "解除"按钮
```
最终改用 class 选择器彻底解决：`document.querySelectorAll('.btn-alarm-on, .btn-alarm-off')`。

## 问题 8：ESP8266 自动连接 WiFi 的处理

### 现象
ESP8266 出厂 AT 固件有自动连接功能，上电后自动连上次的 WiFi。

### 建议
**不要依赖自动连接**。在 STM32 AT 初始化中显式执行 `AT+CWJAP`：
- 已连上时返回 `ALREADY CONNECTED` 不会出错
- 没连上时会正常执行连接
- 关键是要等待 DHCP 拿到 IP（8 秒 delay）

## 调试方法论总结

| 方法 | 场景 |
|------|------|
| **LED 二分法** | 在不同代码位置控制不同 LED 闪烁，定位卡死点 |
| **逐条加回法** | 从最小可工作代码开始，逐条加回指令直到复现故障 |
| **缓冲区检查** | 怀疑数据被污染时，检查缓冲区残留数据 |
| **PC IP 实时核对** | 手机热点 DHCP 分配 IP 可能变化，先 `ipconfig` 确认 |
| **Python 端日志** | main.py 终端会显示 `✅ ESP8266 已连接`，确认 TCP 握手成功 |

## 快速排查流程（如果整套不工作）

1. **检查硬件**: ESP8266 EN/CH_PD 接 3.3V？GPIO0 接 3.3V？GND 共地？
2. **检查供电**: 万用表测 ESP8266 VCC 是否稳定 3.3V
3. **LED 自检**: 红灯闪 3 次？→ 启动正常。黄灯闪 2 次？→ AT 初始化正常
4. **PC IP**: `ipconfig` 确认是 `192.168.4.140`
5. **Python 端**: main.py 显示 `✅ ESP8266 已连接`？
6. **按钮测试**: 点报警 → STM32 LED 亮？蜂鸣器响？
7. **摄像头**: `192.168.4.183:81/stream` 能在浏览器打开？
