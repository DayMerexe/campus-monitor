# 多对话协作流程

## 对话分工

| 对话 | 职责 | 入口文档 |
|------|------|---------|
| **主对话**（此处） | 架构决策、审查 diff、执行合并、进度管理 | `CLAUDE.md` |
| **帧率优化** | ESP32-CAM 固件 + Python 采集优化 | `docs/ESP32-CAM帧率问题.md` |
| **数据传输** | HTTP/MQTT/DB 稳定性修复 | `docs/数据传输问题总结.md` |

新增对话时：复制 `docs/入口文档模板.md` → 填写任务描述 → 更新上表。

---

## 跨层协调原则

| 情况 | 怎么处理 |
|------|---------|
| 问题只在一层 | 派给负责那层的子对话，独立完成 |
| 问题跨两层但改动互不依赖 | 拆成两个任务，各自派发，标 `[关联]` |
| 问题跨两层且改动紧密耦合 | 主对话自己来，不往下派 |

主对话是跨层粘合剂，跨层复杂度不交给子对话承担。

---

## 信息传递机制

每个对话通过 **入口文档** 交换信息，六个区段：

1. **任务描述**（主对话写，子对话可追加）— 问题现象、根因分析、涉及文件
2. **测试用例**（子对话写，算法/逻辑改动时必填）— 输入、预期输出、边界情况
3. **协作进度**（子对话写）— 完成一项更新一项，含日期，bugfix 标 `[bugfix]`
4. **产出清单**（子对话写）— 分支名 + commit hash + 改动摘要，供主对话审查合并
5. **审查反馈**（主对话写，子对话修复后标注）— 审查发现的问题逐条列出，子对话逐条改、逐条标 `[已修复]`
6. **任务总结**（子对话写，任务彻底完成后填）— 做了什么、踩了什么坑、怎么解决的、留给后续的注意事项

子对话启动后第一步：**读取入口文档**（含任务上下文，无需主对话复述）。
子对话调研中发现入口文档未覆盖的新问题时，在"任务描述"末尾追加 `[新发现]` 条目。主对话审查时一并评估，决定是否纳入本次修复还是另开任务。

**交叉依赖标注：** 如果某个问题涉及另一个对话的领域（如 mDNS 需 Python 端 + ESP32 固件端配合），在任务描述中标注 `[关联: <对话名>]`，并在合并指南中注明跨对话依赖。

## 跨层任务分配流程（方案竞标）

新需求涉及两个子对话领域时，用"方案竞标"决定归属，不是主对话直接指派。

### 流程

```
新需求出现（跨两个领域）
          │
          ▼
主对话: 写入入口文档 [待分配] 区段（只写需求描述，不指定由谁做）
          │
          │  通知两边子对话：入口文档有 [待分配]，请各自出方案
          │
    ┌─────┴─────┐
    ▼           ▼
 子对话A      子对话B
 读需求        读需求
 写方案:       写方案:
 ·为什么我适合   ·为什么我适合
 ·我打算怎么做   ·我打算怎么做
 ·需要对方配合什么 ·需要对方配合什么
    │           │
    └─────┬─────┘
          ▼
 双方读对方方案 → 各自给出推荐（A 做 / B 做 / 合做）
          │
          ▼
 主对话看两份方案 + 两份推荐 → 最终裁决
          │
    ┌─────┴─────┐
    │           │
 判给A        判给B
    │           │
    ▼           ▼
 [待分配] 移入该对话的任务描述
 另一方在入口文档标注 `[关联: <执行对话>]` 关注即可
```

### 方案模板

子对话提交方案时写入入口文档的 `[待分配]` 下方：

```
### 方案：<子对话名>

**为什么我适合：** <我的领地优势、已有上下文>

**打算怎么做：** <技术路线、涉及文件、预计改动范围>

**需要对方配合：** <另一方需要提供什么、不改什么>
```

### 裁决原则

- 不争谁"强"，争谁的改动面最小、耦合最低、引入的新依赖最少
- 改动落在单一架构层内的方案优先
- 主对话拥有最终裁决权，子对话的推荐是参考意见

## 代码修改流程（git 分支，默认）

```
子对话: git checkout -b feature/<对话缩写>-<任务> → 读入口文档 → 直接改文件 → 自测 → git commit → 更新入口文档
         ↓
主对话: git diff main...feature/<对话缩写>-<任务> → 审查 → git merge → git branch -d → git commit（如有 merge commit）
         ↓
主对话: 更新 PROGRESS.md
```

### 关键规则

- **子对话必须先切分支再动手**：改任何文件前执行 `git branch --show-current` 确认当前不在 `main`。在 main 上改了一行也算越权
- **子对话在分支内改**：不影响 main，改动隔离在 feature 分支内
- **一个分支 = 一个问题**：不同问题用不同分支，合并互不干扰
- **commit message 清晰**：标注关联的入口文档，如 `fix(esp32): 提高采样频率 (ref: docs/esp32-optimize.md)`
- **合并后删分支**：git 历史已保留所有改动，分支本身无需保留
- **主对话未说合并 = 不能合并**：审查完只生成报告，等用户下达合并指令后才能 `git merge`。用户是最终决定者
- **冲突时手动解决**：git 会标记冲突文件，主对话审查后决定取舍

### `_fixed` 副本（无 git 时备选）

项目未初始化 git 或不需要版本控制时使用：

```
子对话: 读入口文档 → 改 _fixed 副本 → 自测 → 更新"协作进度"→ 更新"产出清单"
主对话: diff 原文件 vs _fixed → 审查 → cp 合并 → 更新 PROGRESS.md
```

## 审查执行流程

子对话提交 feature 分支后，由用户决定何时触发审查。审查采用后台 Agent 执行，不打断主对话讨论。

### 触发方式

```
用户: "审一下对话B的产出"
  ↓
主对话: spawn 后台 Agent（读入口文档 + git diff main...feature/xxx）→ 立刻回来继续讨论
  ↓
Agent 后台完成 → 系统通知用户
  ↓
用户: 自然停顿时说 "看下审查结果"
  ↓
主对话: 读 Agent 报告 → 判断是否合并 → git merge feature/xxx → git branch -d
  ↓
  切回讨论
```

### 分工

| 环节 | 谁做 | 方式 |
|------|------|------|
| 调度审查时机 | **用户** | 用户指令 |
| diff + 生成报告 | Agent | 后台（不阻塞主对话） |
| 判断是否合并 | 主对话 | 前台，收到用户指令后 |
| 执行 merge、删分支 | 主对话 | 前台 |

### 原则

- **Agent 只读不改** — git diff、读文件、生成报告，不执行 merge/commit
- **合并由主对话执行** — git merge、git branch -d 由主对话前台执行
- **用户控制节奏** — 子对话产出后不会自动推送，等用户调度

## 审查反馈循环

主对话审查发现问题时，**直接写入入口文档**，不走人工传话。

### 流程

```
主对话审查发现 N 个问题
        │
        ▼
主对话: 在入口文档 "审查反馈" 区段逐条列出（标注发现时间）
        │
    ┌───▼───┐
    │ 子对话 │ ← 读取入口文档的 "审查反馈"
    │ 逐条改 │
    │ 改完一条 → 在反馈条目下标注 [已修复] + 说明
    │ git commit --amend 或新 commit
    │ 更新 "协作进度"
    └───┬───┘
        │
        ▼
主对话: 重新审查 → git diff 确认改动
        │
   ┌────┴────┐
   │         │
 问题全解决   还有问题
   │         │
   ▼         ▼
 git merge  继续追加反馈
 删分支      回到上一步
```

### 入口文档审查反馈区段格式

```markdown
---

## 审查反馈
_主对话审查后在此逐条列出问题，子对话修复后标注 `[已修复]`。_

| # | 日期 | 问题 | 状态 | 修复说明 |
|---|------|------|------|---------|
| 1 | YYYY-MM-DD | xxx | 待修复 | |
```

子对话修复一条更新一条，主对话复查后在该行打 `✓` 确认。

### 关键规则

- **反馈写在入口文档里**：主对话审查发现问题直接追加到反馈区段，不通过用户口头传话
- **子对话改完标注**：修复后在 "修复说明" 列写做了什么、写在哪行
- **小修用 amend**：改动不大的用 `git commit --amend`，不额外产生 commit
- **大修用新 commit**：涉及多文件或差别大的，新 commit 标注 `fix(review): 响应审查反馈`

## 子对话启动模板

新开对话，第一条消息：

```
【对话名】<对话名称>
【任务入口】docs/<entry-doc>.md
【协作规范】docs/协作流程.md
请先读取这两个文件，了解任务范围、协作规则和当前进度。
然后执行：
  1. git branch --show-current 确认当前位置
  2. git checkout -b feature/<对话缩写>-<任务名> 创建/切换到工作分支（你必须在 feature 分支上改代码）
本次要处理：<具体问题描述>
```

---

## 子对话工作原则

1. **改代码前必须 `git branch --show-current`** — 确认在 feature 分支上。不在则 `git checkout -b feature/<缩写>-<任务>` 先建分支再改。绝不在 main 改东西
2. **入口文档要具体** — 含文件路径、行号、已知结论，别让子对话重新调研
3. **一个对话只做一个架构层** — 不碰其他层的代码，避免跨层改动冲突。跨层由主对话协调
4. **独立任务并行开** — 互不依赖时可以同时进行，各自在独立分支
5. **完成一项立刻更新入口文档** — 不堆积，主对话能实时看到进度
6. **不跑 save-progress** — 子对话只更新入口文档的"协作进度"和"产出清单"。项目的 CLAUDE.md 和 PROGRESS.md 由主对话统一维护
7. **遇到入口文档没写清的问题** — 在"协作进度"里标记 `[待确认]`，主对话来决策
8. **提交前自测** — commit 前确认：编译通过、无意外改动、diff 范围符合预期
9. **bugfix 自治** — feature 分支上自己引入的 bug，三问判断可否直接修：
   - 改动文件是否在原任务指定范围内？
   - 是否影响其他对话的领域？
   - 是否需要改配置或新增依赖？
   三问全"否"→ 直接 commit，协作进度写 `[bugfix]` 简短说明，不走审查反馈循环。任一"是"→ 标 `[待确认]`，等主对话决策
10. **算法/逻辑改动需提供测试用例** — 涉及算法、条件判断、参数计算的改动，在入口文档"测试用例"区段列出：输入什么、预期输出什么、边界情况
11. **改错了不慌** — `git checkout -- <file>` 丢弃改动，或 `git reset --hard` 回退
12. **交叉需要别的对话配合** — 入口文档标注 `[关联: <对话名>]`，由主对话协调
13. **任务彻底完成后填写总结** — 分支已合并、不再改动时，在入口文档"任务总结"区段写：做了什么、踩了什么坑、怎么解决的、留给后续的注意事项。主对话审查确认后封档

## 主对话审查清单

合并前逐项确认：

- [ ] **用户已明确下达合并指令**（主对话不得擅自合并，审查完只报告不等同于可以合）
- [ ] `git diff main...feature/xxx` 变更范围符合入口文档描述（无越权修改）
- [ ] 新增的 import/依赖是否合理
- [ ] 是否引入新配置项（如有，更新 CLAUDE.md）
- [ ] 与 main 分支无冲突（如有冲突已手动解决）
- [ ] commit message 包含入口文档引用
- [ ] 更新入口文档状态（产出清单标注"已合并"）
