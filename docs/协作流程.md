# 多对话协作流程

## 对话分工

| 对话 | 职责 | 入口文档 |
|------|------|---------|
| **主对话**（此处） | 架构决策、审查 diff、执行合并、进度管理 | `CLAUDE.md` |
| **帧率优化** | ESP32-CAM 固件 + Python 采集优化 | `docs/ESP32-CAM帧率问题.md` |
| **数据传输** | HTTP/MQTT/DB 稳定性修复 | `docs/数据传输问题总结.md` |

新增对话时：复制 `docs/_入口文档模板.md` → 填写任务描述 → 更新上表。

---

## 信息传递机制

每个对话通过 **入口文档** 交换信息，三个区段：

1. **任务描述**（主对话写，子对话可追加）— 问题现象、根因分析、涉及文件
2. **协作进度**（子对话写）— 完成一项更新一项，含日期
3. **产出清单**（子对话写）— `_fixed` 文件列表 + 自测结果，供主对话合并

子对话启动后第一步：**读取入口文档**（含任务上下文，无需主对话复述）。
子对话调研中发现入口文档未覆盖的新问题时，在"任务描述"末尾追加 `[新发现]` 条目。主对话审查时一并评估，决定是否纳入本次修复还是另开任务。

**交叉依赖标注：** 如果某个问题涉及另一个对话的领域（如 mDNS 需 Python 端 + ESP32 固件端配合），在任务描述中标注 `[关联: 帧率优化]`，并在合并指南中注明跨对话依赖。

## 代码修改流程

```
子对话: 读入口文档 → 改 _fixed 副本 → 自测（编译/import/diff）→ 更新"协作进度"→ 更新"产出清单"
         ↓
主对话: 读入口文档 → diff 原文件 vs _fixed → 审查 → 合并 → 标记"已合并"
         ↓
主对话: git commit → 更新 PROGRESS.md → 删除 _fixed
```

### 关键规则

- **_fixed 必须是完整文件**，不是代码片段。主对话用 `git diff` 审查，不是人工拼接。
- **一个 fix = 一个问题 × N 个文件**。联动优化（如帧率提升同时改 .ino + .cpp + .py）在产出清单中列出所有 `_fixed`，主对话作为一个 commit 合并。
- **不同问题分开提交**。问题 A 的 `_fixed` 和问题 B 的 `_fixed` 分两次合并，不混在一起。
- **子对话不动原文件**。只写 `_fixed` 副本。
- **_fixed 合并后立即删除**，避免堆积混淆。

### Git 分支（可选替代方案）

子对话产出稳定、主对话信任度高了之后，可以改用分支协作：

```
子对话: git checkout -b fix/xxx → 直接改原文件 → git commit → 更新入口文档
主对话: git diff main...fix/xxx → 审查 → git merge fix/xxx → git branch -d fix/xxx
```

区别：`_fixed` 是 **pre-commit 审查**（主对话是最后一道门），分支是 **post-commit 审查**。初期建议用 `_fixed`，流程跑顺后再考虑分支。

## 审查执行流程

子对话产出 `_fixed` 后，由 **你（用户）** 决定何时触发审查。审查采用 Agent 后台执行，不打断主对话讨论。

### 触发方式

```
你: "审一下对话B的产出"
  ↓
我: spawn 后台 Agent（读 _fixed + diff 原文件）→ 立刻回来继续讨论
  ↓
Agent 后台完成 → 系统通知你
  ↓
你: 自然停顿时说 "看下审查结果"
  ↓
我: 读 Agent 报告 → 判断是否合并 → 执行（cp + git commit + 清理 _fixed）
  ↓
  切回讨论
```

### 分工

| 环节 | 谁做 | 方式 |
|------|------|------|
| 调度审查时机 | **你** | 用户指令 |
| 读文件 + 生成 diff | Agent | 后台（不阻塞主对话） |
| 判断是否合并 | 我（主对话） | 前台，收到你的指令后 |
| 执行合并、提交 | 我（主对话） | 前台（破坏性操作，不做自动） |

### 原则

- **Agent 只读不改** — 读原文件、读 _fixed、生成 diff，不碰文件系统写入
- **合并由我执行** — `cp`、`rm`、`git commit` 是破坏性操作，Agent 不代劳
- **你控制节奏** — 子对话产出后不会自动 push 到我脸上，等你调度

## 子对话启动模板

新开对话，第一条消息：

```
【任务入口】docs/ESP32-CAM帧率问题.md（或其他入口文档）
【协作规范】docs/协作流程.md
请先读取这两个文件，了解任务范围、协作规则和当前进度。
本次要处理：<具体问题描述>
```

---

## 子对话工作原则

来自实践总结：

1. **入口文档要具体** — 含文件路径、行号、已知结论，别让子对话重新调研
2. **一个对话只做一个领域** — 帧率的不碰数据传输，避免冲突
3. **独立任务并行开** — 帧率和数据传输互不依赖，可以同时进行
4. **完成一项立刻更新入口文档** — 不堆积，主对话能实时看到进度
5. **遇到入口文档没写清的问题** — 在"协作进度"里标记 `[待确认]`，主对话来决策
6. **产出前自测** — 更新"产出清单"前确认：文件能编译/import、`diff` 原文件变更范围符合预期、无意外改动

---

## 主对话审查清单

合并前逐项确认：

- [ ] `diff` 变更范围是否符合入口文档描述（无越权修改）
- [ ] 新增的 import/依赖是否合理
- [ ] 是否引入新配置项（如有，更新 CLAUDE.md）
- [ ] 与原文件逻辑无冲突
- [ ] 合并后删除 _fixed，更新入口文档状态
