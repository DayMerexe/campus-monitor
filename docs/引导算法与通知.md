# 人流引导算法 + 钉钉通知内容优化

## 任务描述

### 问题 1：人流引导算法不够智能

**现象：**
当前 `coordinated_decision()` 中的引导逻辑只有一行：

```python
recommended_exit = min(safe, key=lambda ch: snap[ch]['count'])
```

永远推荐人数最少的安全通道。具体问题：

1. **不该引导时也在引导**：三条通道都低于黄色阈值（比如 A=5, B=3, C=2），系统仍推荐 C。实际上所有通道都畅通，不应该"引导"。
2. **只推荐一个出口**：如果 B=2, C=3 都畅通，系统只推荐 B。实际上两个出口都可以走，应该提供"推荐 B 或 C"而非单一出口。
3. **不考虑通道是否活跃**：暂停监测的通道 count=0，会被算法当作"最安全"推荐——实际上这个通道可能根本没开。
4. **缺少"相对拥挤度"概念**：只看绝对人数，不比较各通道相对其阈值的饱和度。比如 A 阈值 20 当前 18（饱和 90%），B 阈值 5 当前 4（饱和 80%），人数少的 B 不一定更安全。
5. **无降级策略**：所有安全通道都接近阈值时，应该给出不同建议（如"各通道均接近饱和，建议分批通行"）。

**涉及文件：**
- `campus_monitor/detector.py`：`coordinated_decision()` 函数（约 L197-289）

### 问题 2：钉钉通知内容需要配合算法

**现象：**
通知内容硬编码推荐单一出口（`alarm_notify()` 中 `rec` 只有一个值），算法改后通知也要跟进：

1. **推荐出口可能不止一个**：算法输出多出口后，通知应列举所有可行出口。
2. **正常状态不该发引导**：算法加了"无需引导"状态后，通知也不应包含引导信息。
3. **饱和度信息缺失**：当前通知只写人数，不写"该通道容量 20 人，当前已达 90%"，缺乏上下文。
4. **恢复通知太简单**：`alarm_clear_notify` 只写"报警已解除"，在复杂场景（如 A 恢复但 B 仍拥挤）应有更丰富的状态描述。

**涉及文件：**
- `campus_monitor/notify.py`：`alarm_notify()`、`alarm_clear_notify()`、`_get_channel_state()`

**关联：** 问题 1 的算法输出是问题 2 的输入，两个问题需要同一次修改联动。
