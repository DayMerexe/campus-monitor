| 组件 | 型号/参数 | 说明 |

| TCP Server | Python (端口 8888) | 广播报警指令到 ESP8266 |

### 硬件接线

```
STM32              ESP8266 ESP-01S
──────────────────────────────────
PA2  (USART2_TX) → RX
PA3  (USART2_RX) → TX
3.3V              → VCC
3.3V              → CH_PD (EN)  ← 必须拉高，否则模块不工作
3.3V              → RST (内部上拉，可悬空)
GND               → GND
```

**供电注意：**
- ESP-01S 工作电压 3.3V，**严禁直接接 5V**
- 推荐使用**独立 3.3V 电源模块**（如 USB 转 3.3V），不要仅依赖 STM32 的 3.3V 引脚，ESP8266 WiFi 发射时瞬时电流可达 300mA+
- CH_PD (EN) 必须拉高到 3.3V，否则模块处于关闭状态

## 问题 1：串口接收架构 —— 轮询 vs 中断

**对应文件**: `F:/bishe/stm32_serial_led/Src/main.c` 第 154-183 行

### 现象
- 使用中断接收时，`HAL_UART_RxCpltCallback` 回调中读到的 `rx_byte` 永远为 0
- `huart.RxState` 变为 `HAL_UART_STATE_BUSY_RX`，后续 `HAL_UART_Receive` 返回 `HAL_BUSY`

### 根因
中断回调在 ISR 上下文中执行。全局变量 `rx_byte` 未正确初始化，回调中拿到始终为 0。回调执行后未重启 `HAL_UART_Receive_IT`，状态机锁死在 BUSY_RX。

### 解决方案
**采用纯轮询模式**，彻底禁用中断接收及回调：

```c
while (1) {
    uint8_t ch;
    if (HAL_UART_Receive(&huart2, &ch, 1, 1) == HAL_OK) {
        HAL_GPIO_TogglePin(GPIOB, GPIO_PIN_5);  // 收到数据翻转 LED0
        // ... 处理 ch
    }
}
```

## 问题 2：数据解析协议 —— \n 依赖陷阱

**对应文件**: `F:/bishe/stm32_serial_led/Src/main.c` 第 163-183 行

### 现象
SSCOM 发送数据时没有自动附带换行符，协议代码依赖 `\n` 才能触发 `sscanf`。

### 根因
不同串口工具换行行为不一致。即使 Python 端广播带有 `\n`，ESP8266 透传可能因分包而缺少。

### 解决方案
改为**逐字节处理**，不依赖终止符：

```c
if (ch != '\r' && ch != '\n') {
    rx_buf[rx_idx++] = ch;
    if (rx_idx >= 63) rx_idx = 0;
    rx_buf[rx_idx] = '\0';

    int count = 0, alarm = 0;
    if (sscanf(rx_buf, "COUNT:%d,ALARM:%d", &count, &alarm) == 2) {
        // 触发动作
        rx_idx = 0;
    }
}
```

## 问题 3：PA3 浮空噪声

**对应文件**: `F:/bishe/stm32_serial_led/Src/usart.c` 第 142-144 行

### 现象
ESP8266 未连接时，`HAL_UART_Receive` 不断读到随机字节，`rx_buf` 被垃圾填满。

### 根因
PA3 配置为 `GPIO_MODE_INPUT` + `GPIO_NOPULL`，浮空状态下电平不确定，USART 外设误判起始位。

### 解决方案
- 当前设计 ESP8266 始终连接，配合问题 6 的缓冲区清空机制即可
- 如需更健壮：给 PA3 配置内部上拉 `GPIO_PULLUP`

## 问题 5：AT 初始化导致 STM32 卡死

**对应文件**: `F:/bishe/stm32_serial_led/Src/main.c` 第 111-127 行

### 现象
含完整 AT 初始化代码的固件烧录后 STM32 不启动（LED 全无闪烁），不含 AT 代码的最小固件正常工作。

### 排除过程（逐条加回法）
| 测试 | 命令 | 结果 |
|------|------|------|
| 1 | `AT\r\n` | ✅ |
| 2 | `AT+CIPSTART` | ✅ |
| 3 | `AT+CIPMODE=1` + `AT+CIPSEND` | ✅ |

### 最终验证的指令序列

```c
HAL_Delay(2000);      // 等 ESP8266 启动
HAL_UART_Transmit(&huart2, (uint8_t*)"AT\r\n", 4, 100);
HAL_Delay(500);

HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWMODE=1\r\n", 13, 100);
HAL_Delay(500);

// ⚠️ 连接 WiFi — 至少 8 秒等 DHCP
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWJAP=\"test\",\"wxh708023\"\r\n", 31, 200);
HAL_Delay(8000);

// 连接 TCP — 3 秒握手
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSTART=\"TCP\",\"192.168.4.140\",8888\r\n", 43, 500);
HAL_Delay(3000);

// 进入透传
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPMODE=1\r\n", 14, 100);
HAL_Delay(500);
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSEND\r\n", 13, 100);
HAL_Delay(500);
```

**关键延时：**
| 阶段 | 延时 | 原因 |
|------|------|------|
| ESP8266 上电 | 2000ms | 模块启动初始化 |
| AT+CWJAP 后 | **8000ms** | WiFi 关联 + DHCP 分配 |
| AT+CIPSTART 后 | 3000ms | TCP 三次握手 |
| 其他 | 500ms | AT 响应时间 |

## 问题 6：TCP 连接成功但 STM32 不收数据（最隐蔽 Bug）

**对应文件**: `F:/bishe/stm32_serial_led/Src/main.c` 第 129-135 行

### 现象
- Python TCP Server 显示 ESP8266 已连接
- 网页按钮点击后提示"已发送"
- `POST /control` 返回 200
- **但 STM32 LED 和蜂鸣器完全不响应**

### 根因分析（全程最隐蔽的 Bug）

1. AT 初始化期间，ESP8266 回复了大量数据：
   ```
   AT\r\n\r\nOK\r\n
   AT+CWMODE=1\r\n\r\nOK\r\n
   WIFI CONNECTED\r\nWIFI GOT IP\r\n\r\nOK\r\n
   CONNECT\r\n\r\nOK\r\n
   AT+CIPMODE=1\r\n\r\nOK\r\n
   AT+CIPSEND\r\n\r\n>
   ```

2. STM32 初始化期间没有消费 USART2 接收缓冲区，这些字节堆积在硬件 FIFO 中

3. 进入 `while(1)` 后，`HAL_UART_Receive` 读到的是 AT 回复残留数据，而非 TCP 透传的 `COUNT:0,ALARM:1`

4. 垃圾数据填满 `rx_buf`，`rx_buf[0]` 是 `'A'`（来自 `AT`），`sscanf(rx_buf, "COUNT:%d,ALARM:%d", ...)` 永远无法匹配

### 解决方案
进入 `while(1)` 前清空 USART2：

```c
{
    uint8_t dump;
    while (HAL_UART_Receive(&huart2, &dump, 1, 2) == HAL_OK) {}
}
memset(rx_buf, 0, sizeof(rx_buf));
rx_idx = 0;
```

- `2ms` 超时逐字节读空，缓冲区空后返回 `HAL_TIMEOUT`
- `memset` 确保 `rx_buf` 从头干净
