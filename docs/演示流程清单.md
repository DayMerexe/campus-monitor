## 演示前准备（答辩开始前 10 分钟）

### 硬件上电

- [ ] ESP32-CAM 插电（指示灯亮）
- [ ] PC 开机，连接 WiFi：`test` / `wxh708023`
- [ ] ESP8266 + STM32 插电
- [ ] 观察 STM32 LED：
  - [ ] 红灯闪 3 次 → STM32 启动正常
  - [ ] 黄灯闪 2 次 → ESP8266 初始化完成

### 软件启动

- [ ] 双击 `F:\bishe\start.bat`
- [ ] 确认终端显示：`🚀 Web 服务已启动: http://localhost:5000`
- [ ] 确认终端显示：`✅ ESP8266 已连接: ('192.168.4.xxx', ...)`
- [ ] 浏览器打开 `http://localhost:5000` 确认画面正常

### 备用

- [ ] 手机热点开启：`test` / `wxh708023`（万一 ESP32-CAM 热点挂了）
- [ ] 项目文件夹 `F:\bishe\` 在桌面上创建快捷方式

## 演示流程（约 5-8 分钟）

### 第1步：展示系统界面（30 秒）

**操作**：浏览器指向 `localhost:5000`

**讲解要点**：
- "这是系统的 Web 仪表盘，左边是实时视频流，右边是统计数据和趋势图"
- "可以看到当前人数、报警状态、今日检测总数等"

**注意**：用手指向屏幕上的各个区域，不要只是说

### 第2步：正常检测演示（1 分钟）

**操作**：在摄像头前走动

**讲解要点**：
- "摄像头拍摄画面后，YOLOv8 AI 模型实时识别行人"
- "可以看到画面中的人被绿色框标出，右上角计数实时更新"
- "右侧折线图同步更新人数变化趋势"

**预期结果**：
- 视频画面中有绿色检测框
- `当前人数` 数字变化
- 折线图更新

### 第3步：报警触发演示（2 分钟）

**操作**：
- 找人一起站到摄像头前，凑够 5 人以上
- 或者：将网页上的阈值调低到 1 或 2

**讲解要点**：
- "系统设置了报警阈值，当前为 5 人"
- "超过阈值后，系统会自动触发报警"
- "看，页面出现红色报警横幅，同时 STM32 的 LED 亮起、蜂鸣器响"

**预期结果**：
- 页面显示红色 `⚠️ 超过阈值！请立即疏散！`
- 报警状态变为 `⚠️ 报警中`
- STM32 红灯亮 + 蜂鸣器响
- 报警历史表格新增一条记录

### 第4步：手动控制演示（1 分钟）

**操作**：
- 点击网页上的 `⚠️ 报警` 按钮
- 等待 STM32 响应
- 点击 `解除` 按钮

**讲解要点**：
- "除了自动报警，管理员也可以手动控制"
- "这在紧急情况下可以远程启动疏散警报"
- "TCP 指令通过 WiFi 发送到 ESP8266，再由串口传给 STM32"

**预期结果**：
- 点击报警 → STM32 LED/蜂鸣器响应
- 点击解除 → STM32 恢复

### 第5步：阈值动态调节（30 秒）

**操作**：
- 在输入框中修改阈值，点击"设置"
- 观察弹窗确认

**讲解要点**：
- "阈值可以在线动态调整，适应不同场景"
- "比如上课时间人多，可以调高阈值减少误报"

### 第6步：报警历史查询（30 秒）

**操作**：滚动页面到底部的报警历史表格

**讲解要点**：
- "所有报警事件都记录在数据库中"
- "包括开始时间、结束时间、峰值人数和持续时长"
- "方便事后复盘分析"

## 可能遇到的问题及应对

| 问题 | 应对 |
|------|------|
| 摄像头画面不显示 | 浏览器直接访问 `192.168.4.121:81/stream` 测试。不行就重启 ESP32-CAM |
| YOLO 检测不到人 | 确认人站在摄像头视野内。调低阈值为 1 测试报警逻辑 |
| STM32 不响应 | 看终端是否有 `✅ ESP8266 已连接`。没有就按 STM32 复位键 |
| 网页打不开 | 确认终端有 `🚀 Web 服务已启动`。检查防火墙是否拦截 5000 端口 |
| WiFi 连不上 | 重启 ESP32-CAM（它会自动创建热点） |
| 演示中出 bug | 直接说"这个功能我们在测试时是正常的，可能是现场网络干扰" |
| 导师问为什么用这个方案 | 见下方 Q&A |

## 答辩常见 Q&A

### Q1：为什么用 YOLOv8 而不是其他模型？
**答**：YOLOv8n 是轻量级模型，只有 3.2M 参数，在 CPU 上也能跑 10-15 FPS，满足实时性要求。同时它精度高、部署简单，一行代码就能加载。

### Q2：为什么不用 MQTT？
**答**：项目通信拓扑是一对多（PC 到多个 STM32），TCP 透明传输模式更简单直接。MQTT 需要额外部署 Broker，增加了系统复杂度。而且 ESP8266 的 AT 固件对 MQTT 支持不够完善。

### Q3：帧率为什么只有 10-15 FPS？
**答**：目前是在笔记本 CPU 上跑推理。后续可以部署到 Jetson Nano 或使用 GPU，帧率可以提升到 30+ FPS。另外优化预处理分辨率（320×240）已经比全帧检测快了 4 倍。

### Q4：系统稳定性如何？
**答**：PC 端有断线重连和异常处理，摄像头断开会自动重连。TCP 有 keepalive 检测死连接。STM32 端有缓冲区清空和防抖机制。目前连续运行测试未出现死机。

### Q5：能部署到实际校园吗？
**答**：当前是原型验证阶段，证明了技术可行性。实际部署需要：① 专用服务器或 Jetson 替代 PC；② 多个摄像头点位；③ 4G/5G 通信替代 WiFi。这些是下一步计划。

### Q6：创新点在哪里？
**答**：① 全链路打通：摄像头 → AI → Web → 硬件的完整数据闭环；② 报警防抖机制：多帧确认 + 锁定时间，解决误触发问题；③ 透明传输模式选型：简化了 STM32 端的解析逻辑。
