# ESP8266 TCP 通信模式选型：普通模式 vs 透明传输模式

## 背景

用 AT 固件的 ESP8266 做 TCP Client，通过 WiFi 连 PC 上的 Python TCP Server，接收报警指令发给 STM32。

---

## 问题起源

初学 ESP8266 AT 指令时，网上搜索到的资料几乎都在讲"普通模式"，所有 TCP 接收示例都这样处理 `+IPD,N:` 前缀：

```
+IPD,19:COUNT:3,ALARM:1
```

但实际调试时发现：
1. 普通模式需要手动解析 `+IPD,N:` 前缀，`N` 是数据长度
2. `+IPD` 包含 TCP 分片语义，一帧数据可能被拆成多个 `+IPD`
3. STM32 端用 `sscanf` 解析 `+IPD,N:COUNT:...` 远比 `COUNT:...` 复杂
4. 网络搜索结果中几乎没有中文资料讲透明传输模式如何用

---

## 两种模式对比

| | 普通模式 (默认) | 透明传输模式 (CIPMODE=1) |
|---|---|---|
| **TCP 收到 `COUNT:3,ALARM:1\n`** | 串口输出 `+IPD,19:COUNT:3,ALARM:1` | 串口输出 `COUNT:3,ALARM:1` |
| **从串口发 `HELLO`** | 需要 `AT+CIPSEND=5` 再发数据 | 直接发 `HELLO` |
| **STM32 解析难度** | 高，需要处理 `+IPD` 前缀和分片 | 低，直接 `sscanf` 匹配 `COUNT:%d,ALARM:%d` |
| **AT 命令响应** | 能收到 `OK` / `ERROR` | 收不到（进入透传后所有数据直通 TCP） |
| **退出方式** | N/A | 发 `+++`（不要带 `\r\n`，隔 1 秒后再发） |

---

## 为什么网上只能搜到 `+IPD` 方案

1. **ESP8266 AT 指令文档以普通模式为主要使用场景**，透传模式仅在新版 AT 固件（v1.7+）中才完善
2. **中文博客 / CSDN 大量抄来抄去**，几乎没人写透传模式实战
3. **大部分 Arduino 教程用 WiFiClient 库**，不走 AT 指令，不存在此选型问题
4. **透传模式关键词** `AT+CIPMODE=1` + `AT+CIPSEND` 在中英文搜索结果中都较少

---

## 最终选型：透明传输模式

### 为什么不用普通模式

若用普通模式处理 `+IPD,19:COUNT:3,ALARM:1`，STM32 需要：

```c
// 普通模式解析 —— 复杂且容易出错
int len = 0;
if (sscanf(rx_buf, "+IPD,%d:", &len) == 1) {
    char *data = strchr(rx_buf, ':') + 1;  // 跳过 ":"
    int count, alarm;
    if (sscanf(data, "COUNT:%d,ALARM:%d", &count, &alarm) == 2) {
        // ...
    }
}
```

问题：
- `+IPD` 分片：一条消息可能被拆成多段 `+IPD`，需要拼接
- 超时处理：TCP 断线时 ESP8266 发 `CLOSED` 而非 `+IPD`，需额外处理
- 内存开销：`rx_buf` 需要容纳 `+IPD,N:` 前缀 + 数据，缓冲区更长

### 用透明模式为什么简单

```c
// 透明模式 —— 数据直达
if (HAL_UART_Receive(&huart2, &ch, 1, 1) == HAL_OK) {
    if (ch != '\r' && ch != '\n') {
        rx_buf[rx_idx++] = ch;
        rx_buf[rx_idx] = '\0';

        int count = 0, alarm = 0;
        if (sscanf(rx_buf, "COUNT:%d,ALARM:%d", &count, &alarm) == 2) {
            // 直接拿到 count 和 alarm
        }
    }
}
```

数据是原样的 `COUNT:3,ALARM:1`，没有前缀，没有分片语义，不需要拼接。

## 透明模式 AT 初始化序列

```c
// 1. 基础测试
HAL_Delay(2000);  // 等 ESP8266 上电启动
HAL_UART_Transmit(&huart2, (uint8_t*)"AT\r\n", 4, 100);
HAL_Delay(500);

// 2. Station 模式
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWMODE=1\r\n", 13, 100);
HAL_Delay(500);

// 3. 连接 WiFi —— 至少 8 秒等 DHCP 拿 IP
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CWJAP=\"test\",\"wxh708023\"\r\n", 31, 200);
HAL_Delay(8000);

// 4. 连接 TCP Server —— 3 秒 TCP 握手
HAL_UART_Transmit(&huart2,
    (uint8_t*)"AT+CIPSTART=\"TCP\",\"192.168.4.140\",8888\r\n", 43, 500);
HAL_Delay(3000);

// 5. 设为透明传输模式
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPMODE=1\r\n", 14, 100);
HAL_Delay(500);

// 6. 进入透传
HAL_UART_Transmit(&huart2, (uint8_t*)"AT+CIPSEND\r\n", 13, 100);
HAL_Delay(500);

// ⚠️ 关键：进入透传后清空 RX 缓冲区，丢弃 AT 响应的残留数据
{
    uint8_t dump;
    while (HAL_UART_Receive(&huart2, &dump, 1, 2) == HAL_OK) {}
}
memset(rx_buf, 0, sizeof(rx_buf));
rx_idx = 0;
```

### 延时说明

| 阶段 | 延时 | 原因 |
|------|------|------|
| ESP8266 上电 | 2000ms | 模块启动初始化 |
| AT+CWJAP 后 | **8000ms** | WiFi 关联 + DHCP 分配 IP 地址 |
| AT+CIPSTART 后 | 3000ms | TCP 三次握手 |
| 其他指令 | 500ms | AT 命令响应时间 |

**总耗时约 15 秒**。如果 ESP8266 已经连过这个 WiFi 并自动连接，`AT+CWJAP` 返回 `ALREADY CONNECTED`，不报错，但 DHCP 延时依然需要。

---

## 踩坑：AT 响应残留污染 rx_buf

### 现象
透传模式设置成功，ESP8266 连上了 TCP Server，但网页发送的 `COUNT:0,ALARM:1` STM32 收不到。

### 根因
AT 初始化期间 ESP8266 回复了大量响应数据：

```
AT
OK
AT+CWMODE=1
OK
WIFI CONNECTED
WIFI GOT IP
OK
CONNECT
OK
AT+CIPMODE=1
OK
AT+CIPSEND
>
```

这些字节全部积压在 USART2 接收缓冲区。进入 `while(1)` 后，`HAL_UART_Receive` 最先读到它们，`rx_buf` 开头变成 `"ATOKAT+CWMODE=1OK..."`，后续的 `COUNT:...` 数据追加在垃圾后面，`sscanf` 从 `rx_buf[0]` 开始匹配，永远得不到正确结果。

### 解决
上面代码中的缓冲区清理步骤（`while(HAL_UART_Receive(...))` + `memset`）。

---

## 总结

| 查找问题的关键词 | 适用场景 | 推荐度 |
|---|---|---|
| `+IPD` | 需要 AT 指令交互、动态切换连接 | ⭐⭐ |
| `AT+CIPMODE=1` (透传) | 固定 TCP 连接、数据量大、接收端 MCU 资源有限 | ⭐⭐⭐⭐⭐ |

**如果你是用 STM32/51/Arduino 作为接收端，且通信协议简单固定（如 `COUNT:x,ALARM:y`），直接用透明传输模式，不要碰 `+IPD`。**
