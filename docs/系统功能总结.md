# 系统功能总结

> 应急场景下的校园人流量监测预警系统 — 毕设项目  
> 更新时间：2026-05-17

---

## 一、系统功能全景

### 1. 视频采集与 AI 检测

| 能力 | 说明 |
|------|------|
| 三通道独立检测 | A/B/C 三路 YOLOv8n 并行推理，每通道独立启停 |
| 双视频源 | MJPEG（ESP32-CAM 实时流）+ MP4（本地文件回放），运行时切换 |
| 多摄像头支持 | MJPEG URL 可输入不同 ESP32-CAM 地址，前端有 ✓ 确认按钮 |
| 视频文件冲突防护 | 同一 MP4 被多通道占用时自动拒绝 |
| 性能优化 | 三通道相位错开防 GPU 争抢，MP4 EOF seek 替代 reopen，JPEG Q60 压缩 |

### 2. 人流监测与报警

| 能力 | 说明 |
|------|------|
| 三级报警 | 🟢 正常 → 🟡 黄色预警 → 🔴 红色报警，每通道独立阈值 |
| 对称防抖 | 连续 3 帧确认升降，防止误触发 |
| 手动报警 | 前端按钮一键触发全局紧急状态 |
| 火灾传感器 | 物理火焰传感器接入 STM32，MQTT 上报实时状态 |
| 火灾模拟 | 前端按钮模拟单通道火灾（API 拒绝已绑物理传感器的通道） |
| 联动决策 | 四策略算法决定全局推荐出口（见下） |

### 3. 人流引导算法

**四策略决策：**

| 策略 | 触发条件 | 行为 |
|------|----------|------|
| `all_clear` | 所有活跃通道畅通 | 无需引导 |
| `guided` | 有拥挤/火灾通道，有畅通替代 | 推荐多出口，按饱和度排序 |
| `degraded` | 所有安全通道接近容量上限 | 建议分批通行 |
| `emergency` | 所有活跃通道火灾 | 紧急疏散 |

**核心改进：** 饱和度 = count / threshold_warn（相对拥挤度），替代绝对人数排序。暂停通道自动排除。

### 4. 硬件控制

| 能力 | 说明 |
|------|------|
| 多 STM32 设备支持 | MQTT 通配符订阅，自动发现新设备 |
| 设备通道绑定 | 每 STM32 绑定到 A/B/C 通道，独立 LV:BUZ:SERVO 指令 |
| 舵机闸门 | LV≥2 触发打开（红色报警或火灾） |
| 蜂鸣器 | LV≥1 触发 |
| 手动报警硬件联动 | manual_alarm_active 参与 LV 计算（与火灾同级 lv=2） |

### 5. 钉钉通知

| 能力 | 说明 |
|------|------|
| 报警通知 | 四策略差异化文案 + 三通道概览 + 饱和度百分比 |
| 恢复通知 | 每通道独立解除 + 附带各通道当前状态 |
| 冷却限流 | 60 秒内同一通道重复报警不重复推送 |
| 应急消息 | 全火灾时的紧急疏散文案 |

### 6. Web 仪表盘

| 能力 | 说明 |
|------|------|
| 三通道实时视频 | MJPEG 流 + MP4 回放，暂停蒙层 |
| 动态折线图 | 仅活跃通道显示，秒对齐时间轴，spanGaps 连线，1s 刷新 |
| 推荐面板 | 四策略 UI 切换（绿/黄/红），多出口文字展示 |
| 通道边框强化 | fire-danger / safe-exit 动态 class |
| 应急双态模式 | 紧急时红色顶部栏 + 折线图折叠 + 推荐面板突出 |
| 响应式 | 移动端 @media (max-width: 680px) 适配 |
| 阈值实时调节 | 前端滑块，即时生效 |
| 视频源切换 | 下拉选择 MP4 文件 / MJPEG URL，运行时切换 |
| 设备绑定面板 | 动态设备列表 + 通道下拉绑定 |

### 7. API 路由（15 个）

| 路由 | 方法 | 用途 |
|------|------|------|
| `/` | GET | 仪表盘页面 |
| `/video_feed/<ch>` | GET | MJPEG 视频流 |
| `/status` | GET | 聚合状态（向后兼容） |
| `/dashboard` | GET | 合并接口（三通道状态 + 推荐 + history + alarms） |
| `/set_threshold/<ch>` | POST | 每通道阈值设置 |
| `/list_videos` | GET | 可用 MP4 文件列表 |
| `/set_source/<ch>` | POST | 切换视频源 |
| `/control` | POST | 手动报警开/关 |
| `/fire_simulate/<ch>` | POST | 火灾模拟 |
| `/bind_stm32` | POST | 设备通道绑定 |
| `/get_bindings` | GET | 设备绑定状态 |
| `/replay/<ch>` | POST | 手动重播视频 |
| `/monitoring/toggle/<ch>` | POST | 监测启停 |
| `/history` | GET | 检测记录 |
| `/alarms` | GET | 报警事件 |

## 三、踩坑记录：问题与解决方案

### 通信与连接

| # | 问题 | 现象 | 根因 | 解决方案 |
|---|------|------|------|----------|
| 1 | **MJPEG 流无法解析** | OpenCV `VideoCapture` 打开 ESP32 MJPEG URL 返回空帧 | OpenCV 的 FFmpeg 后端不兼容 ESP32-CAM 的 MJPEG 格式 | 改用 `requests.get(stream=True)` + `raw.read()` 手动解析 JPEG 边界标记 |
| 2 | **浏览器连接池耗尽** | 开几个标签页后所有 `/video_feed` 都卡死 | 浏览器判 MJPEG 卡死→重连→Flask 旧线程未退出→连接池泄漏 | 前端合并 4 个轮询为 2 个；`generate_frames()` 固定 200ms 发帧 + 时间戳水印，浏览器不判为卡死 |
| 3 | **MJPEG 持久连接断开** | MJPEG 流跑几分钟后画面冻结 | ① 探针 GET→close 占用了 ESP32-CAM 唯一的 MJPEG 槽位 ② `iter_content()` 生成器 GC 关闭底层连接 ③ 多线程共享同一连接数据交叉 | ① 删探针连接直接返回 URL ② 改用 `r.raw.read()` 替代 `iter_content()` ③ 连接缓存 key 改为 `(url, thread_id)` per-thread |
| 4 | **TCP 广播洪水** | STM32 收到乱码/丢指令 | PC 每 200ms 无脑发 TCP，UART 缓冲区溢出 | TCP 广播限速 + 后续直接切换到 MQTT 协议 |
| 5 | **STM32 UART 粘包** | 两条指令拼成一条收到，解析失败 | 累积式 buff 读取无法区分消息边界 | 改为按行分隔（`\n` 作为帧边界） |
| 6 | **MQTT 三通道刷屏** | 三通道同时报警 → broker 收到 3 条/0.5s → 部分丢失 | 三个检测线程同时触发 `broadcast()`，无节流 | 最小发送间隔 0.5s；后续改为 per-device 定向发送替代全局广播 |
| 7 | **broadcast 在锁内死锁** | TCP `broadcast()` 耗时 200ms+，阻塞 `coord_lock`，三个检测线程等锁→画面卡 | `broadcast()` 在 `coordinated_decision()` 的 `with coord_lock:` 内部调用 | `broadcast()` 移出 `coord_lock` 临界区 |

### 视频与检测

| # | 问题 | 现象 | 根因 | 解决方案 |
|---|------|------|------|----------|
| 8 | **ESP32-CAM 帧率异常低** | OV2640 在 20MHz XCLK 下 PLL 无法锁定，实际仅 2-3fps | 20MHz 是 OV2640 规格外频率，PLL 异常 | XCLK 提升至 30MHz + 分辨率降至 QVGA → 实测 20+fps |
| 9 | **MJPEG 源切换画面冻结** | 切换 MJPEG URL 后仍显示旧摄像头的最后一帧 | 切换源时未清 `frame` 缓存，前端 `img.src` 继续渲染旧 JPEG | 源切换时清 `st['frame']=None` + 读帧失败主动清帧 + JPEG 数据校验 |
| 10 | **MP4 源切换路径错误** | 下拉选项值带 `mp4:` 前缀，后端当成文件路径打开失败 | 前端 `option.value = "mp4:" + filename`，传给 API 时没去前缀 | 前端 `substring(4)` 去掉前缀 |
| 11 | **MP4 文件冲突** | 两通道选同一 MP4，`VideoCapture` 重复打开导致帧错乱 | 无冲突检测，两个 detector 线程同时读同一文件 | 前端下拉显示占用标记 + API 端 `toggle_monitoring` 检查冲突返回 409 |
| 12 | **MP4 播完黑屏** | 视频文件播到 EOF 后 `VideoCapture.read()` 返回 `False`，等待期间画面黑屏 | `cv2.VideoCapture` 到 EOF 后不再自动循环 | EOF 时 `set(cv2.CAP_PROP_POS_FRAMES, 0)` seek 回开头，替代 `reopen()` |
| 13 | **三通道 YOLO 同时抢 GPU** | C 通道检测帧率明显低于 A/B | 三个 `detect_loop` 同时启动，YOLO 推理同时抢 CUDA→C 通道被饿死 | 启动时相位错开 ~16.7ms（`time.sleep(0.0167 * i)`） |
| 14 | **密集人群通道更卡** | 7-9 人通道比 3-4 人通道明显卡顿 | YOLO 推理时间与检测框数量正相关，密集帧耗时更长 | 帧率上限 15→20fps + JPEG Q60 压缩减少传输开销 |

### 报警与算法

| # | 问题 | 现象 | 根因 | 解决方案 |
|---|------|------|------|----------|
| 15 | **报警抖动** | 人数在阈值临界线上下波动时报警反复触发/解除 | 单帧判定，无滞后 | 对称防抖：连续 3 帧确认才升降 + 3 秒锁定 |
| 16 | **手动报警不触发硬件** | 前端点"手动报警"→仪表盘红了但舵机蜂鸣器不响 | `manual_alarm_active` 是僵尸变量——设了值但 `coordinated_decision()` 没读取 | 在 `coordinated_decision()` 中 `lv = 2 if (fire or manual_alarm_active) else alarm_level` |
| 17 | **火焰传感器硬编码** | 火焰传感器始终绑通道 A，改不了 | `flame_active` 是全局 OR，不管哪个 STM32 报的火 | 每设备绑定到通道 → `device_bindings[dev_id] = channel` → `snap[ch]['fire']` 按绑定传递 |
| 18 | **引导算法太简陋** | 永远推荐人数最少的安全通道，人多但都畅通时也在"引导" | `recommended_exit = min(safe, key=count)` 一行逻辑 | 四策略决策树：all_clear / guided / degraded / emergency，饱和度 = count/threshold_warn |
| 19 | **火灾通道被忽略** | B 通道火灾但 A、C 畅通 → 算法返回 all_clear "各通道畅通" | all_clear 条件只检查了 `not crowded_chs`，没检查 `fire_channels` | 条件改为 `not crowded_chs and not fire_channels` |
| 20 | **火灾模拟不发通知** | 前端点"火灾模拟"→STM32 响但钉钉没消息 | `fire_simulate()` 只调了 `coordinated_decision()` 没调通知函数 | 显式调用 `alarm_notify(ch, 2, count)` / `alarm_clear_notify(ch, peak)` |

### 前端

| # | 问题 | 现象 | 根因 | 解决方案 |
|---|------|------|------|----------|
| 21 | **阈值输入框被刷新覆盖** | 正在输入阈值数字，被轮询刷新成旧值 | `setInterval` 用 innerHTML 全量替换，覆盖用户输入 | 输入框聚焦时不刷新值（`document.activeElement` 检测） |
| 22 | **折线图永远三条线** | 暂停通道折线还在图上，显示归零线 | Chart.js 始终创建 3 个 dataset，关闭的通道也不移除 | 动态 dataset：只创建活跃通道的线，全停时显示占位提示 |
| 23 | **折线图竖向无限延展** | 数据点多时 canvas 竖向撑爆容器 | `min-height: 260px` + canvas `height: 100%` = 无上限 | 固定 `height: 280px` + `overflow: hidden` |
| 24 | **三通道 X 轴时间戳不对齐** | A/B/C 各用毫秒级时间戳，X 轴上全是散点 | 每通道独立 ISO 时间戳带毫秒，三点从未在秒级对齐 | 前端 `timestamp.split('.')[0]` 截断毫秒，统一秒级 X 轴 |
| 25 | **通道关闭再开显示旧数据** | 重新激活通道后折线图闪现关闭前的历史记录 | 前端用客户端 `channelActiveSince` 过滤，关闭后变量清空，重开时无过滤 | 服务端 `monitoring_start` 追踪激活时间，前端按此过滤 |
